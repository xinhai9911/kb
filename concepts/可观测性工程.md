# 可观测性工程

> 「可观测性」= 通过系统外部输出推断内部状态的能力。三大支柱：日志、指标、追踪。

## 1. 三大支柱

| 支柱 | 回答 | 工具 | 体量 |
|------|------|------|------|
| **日志 (Logs)** | 发生了什么（事件细节） | Loki/ELK | 大、贵、查问题 |
| **指标 (Metrics)** | 系统健康吗（聚合数） | Prometheus | 小、便宜、告警 |
| **追踪 (Traces)** | 一次请求经过哪些服务/耗时 | Jaeger/Tempo | 中、定位延迟 |

> 日志用于「事后查根因」，指标用于「实时告警」，追踪用于「跨服务定位慢点」。三者互补，不能互相替代。

## 2. OpenTelemetry（事实标准）

- OTel 统一了**_trace/metric/log 的数据模型与采集 SDK**，后端可换（Prometheus/Grafana/Jaeger）。
- 核心是 **Context Propagation**：TraceID/SpanID 跨进程、跨协议（HTTP header `traceparent`）传递，串起一次请求的全链路。
- 采集分 **instrumentation**（自动注入如 Java agent / 手动 SDK）与 **Collector**（批处理、导出）。

## 3. Metrics 四类

| 类型 | 语义 | 例子 |
|------|------|------|
| Counter | 只增（累计） | 请求总数、错误数 |
| Gauge | 可增可减瞬时值 | 内存、连接数、队列长度 |
| Histogram | 分布（分桶） | 请求延迟分布 |
| Summary | 分位数近似 | P99 延迟 |

> 延迟一定要用 Histogram/Summary 看**分位数（P95/P99）**，平均值掩盖长尾（见 [[concepts/系统设计思维\|容量与长尾]]）。

## 4. RED 与 USE 方法

- **RED**（服务/请求视角）：Rate（请求率）、Errors（错误率）、Duration（延迟分布）。
- **USE**（资源视角）：Utilization、Saturation、Errors——用于 CPU/内存/磁盘/网络（见 [[entities/CPU 性能分析实战]]、[[concepts/Linux 内核网络栈]]）。

## 5. SLO / SLI / 错误预算

| 项 | 含义 |
|----|------|
| **SLI** | 实际指标（如「99% 请求 < 300ms」） |
| **SLO** | 目标（如「月度 99.9% 可用」） |
| **错误预算** | 允许的失败额度（0.1%/月） |

- 错误预算耗尽 → 冻结新功能、先稳系统。这是**用数据决策发布节奏**的核心机制。
- 告警应基于 SLO，而非「CPU 90%」等底层指标（避免噪声）。

## 6. 追踪上下文传播（关键工程点）

```
Client ──traceparent: trace-id, parent-span-id──► ServiceA
ServiceA 继续派生子 span ──traceparent──► ServiceB
```
- 任何跨线程/跨进程边界都必须**显式传递 context**，否则链路断。
- 异步/消息队列（[[concepts/架构风格演进\|事件驱动]]）要在消息头里带 TraceID。

## 7. 内核/基础设施可观测

- 无需改代码的底层观测用 **eBPF**（[[concepts/eBPF 核心架构]]）：网络、文件、 syscall 级追踪。
- Nginx/网关层可吐访问日志与 stub_status（[[entities/Nginx 性能调优与排障]]）。
- 多层组合：应用 OTel + 内核 eBPF + 主机 node_exporter。

## 8. 常见反模式

| 反模式 | 后果 |
|--------|------|
| 只打日志不采指标 | 无法告警/看趋势 |
| 日志打印敏感/超量 | 成本高、合规风险 |
| 追踪不传 context | 链路断裂 |
| 告警基于资源而非 SLO | 噪声多、狼来了 |
