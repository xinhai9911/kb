# 磁盘分区 文件系统 与 挂载管理

> 前置：[[concepts/Linux 启动链 与 引导]]（引导分区与 UUID 的必要性）。
> 应用：[[concepts/KVM 公有云 镜像 适配]] §3（规范约束）、§6（扩容链路）。

## 1. 分区表：MBR 与 GPT

| 维度 | MBR（msdos） | GPT |
|---|---|---|
| 寻址位宽 | 32 位 LBA → 上限 2 TiB | 64 位 LBA |
| 分区数 | 4 主分区 | 默认 128 |
| 元数据冗余 | 无 | 主表 + 备份表 + CRC32 校验 |
| 类型标识 | 1 字节 type code | 16 字节 GUID |
| UEFI 引导 | 不支持 | 支持 |
| 大容量盘 | 需混合 MBR/超容量 hack | 原生支持 |

```bash
parted -s /dev/vda print | grep 'Partition Table'   # gpt / msdos
lsblk -o NAME,SIZE,FSTYPE,PARTTYPENAME,PARTTYPE
```

## 2. 分区类型与布局实践

### 2.1 引导相关类型（与启动链呼应）

| 用途 | GPT GUID | sgdisk/parted | 大小 |
|---|---|---|---|
| ESP | `C12A7328-…-00A0C93EC93B` | `ef00` / `esp` | 200~600 MiB，FAT32 |
| BIOS boot | `21686148-…-656564454649` | `ef02` / `bios_grub` | 1 MiB |
| Linux 文件系统 | 按 FS 标识 | `8300` | — |

### 2.2 "根分区放最后"的因果（阿里云镜像硬性规范）

`growpart` 只能扩展**分区表末尾**的分区：

```
[vda1 ESP][vda2 /boot][vda3 /  ]            ← / 在末尾：云盘扩容 → growpart 可直接吃掉尾部空间 ✅
[vda1 ESP][vda2 /   ][vda3 /data]           ← / 不在末尾：新增空间在 /data 之后，/ 扩不动 ❌
```

所以云镜像的标准布局是：**ESP → /boot → /（最后一个，吃满剩余）**。

### 2.3 /boot 为什么常独立成区

- GRUB（尤其 Legacy 与某些文件系统组合）对根文件系统支持受限
- 加密/LVM 根时，引导器读不到根 → 需要一个 plain 的 /boot
- 云镜像里保留 /boot 是稳妥做法（本库 appliance 镜像即有 1G /boot）

## 3. 文件系统：XFS 与 ext4

| 维度 | XFS | ext4 |
|---|---|---|
| 在线扩容 | `xfs_growfs <挂载点>` | `resize2fs <设备>` |
| **缩容** | **不支持** | 支持（须离线 + fsck） |
| 元数据日志 | 有 | 有 |
| 大文件/大目录性能 | 强 | 良好 |
| RHEL8 默认根 FS | **是** | — |
| 云镜像常见选择 | XFS（RHEL 系）/ ext4（Debian 系） | — |

```bash
blkid                     # 看 UUID / TYPE / LABEL
df -hT; lsblk -f
```

**关键认知**：fstab 与 grub 用 **UUID**（`blkid` 出的文件系统 UUID）而不是 `/dev/vda3`，
因为设备名随协议/枚举顺序变化（xvda/vda/sda/nvme0n1），UUID 跟着文件系统走。

> 注意别混淆：**分区 UUID**（`PARTUUID`，属于分区表）与**文件系统 UUID**（`UUID`）。
> `lsblk -o NAME,UUID,PARTUUID` 一眼分清。

## 4. 云盘扩容完整链路

```
① host 侧：控制台/API 扩大云盘容量（块设备在 guest 里"变大"了）
② guest 侧：
   growpart /dev/vda 3        # 扩分区（只能扩末尾分区；需 cloud-utils-growpart）
   partprobe /dev/vda         # 必要时让内核重读分区表
   xfs_growfs /               # XFS 在线扩（参数是挂载点）
   resize2fs /dev/vda3        # ext4 用（参数是设备）
③ 核对：df -hT / 与 lsblk 交叉验证
```

**LVM 场景（云版镜像不建议，见 §6）**：

```bash
pvresize /dev/vda3
lvextend -l +100%FREE /dev/klas/root
xfs_growfs /
```

**cloud-init 自动扩容**：`growpart` + `resizefs` 模块在首次启动时执行 ②③，
这是云版镜像"开箱即扩容"的标准做法——但 LVM 链路它不会替你做完。

## 5. 挂载管理：fstab 与 systemd mount 单元

### 5.1 fstab 六列

```
UUID=xxx   /data   xfs   defaults,nofail   0   0
   ↑          ↑      ↑          ↑           ↑   ↑
 设备      挂载点  文件系统    选项        dump  fsck
```

### 5.2 选项语义（云上最常用的是前两个）

| 选项 | 含义 | 云上为什么重要 |
|---|---|---|
| `nofail` | 设备不存在时**不阻塞启动** | 数据盘缺失（换规格/未挂载）时不进 emergency |
| `x-systemd.device-timeout=0` | 不等待设备出现 | 加速启动，避免超时等待 |
| `noauto` | 不在启动时自动挂载 | 与 nofail 不同：**完全不挂** |
| `_netdev` | 等网络就绪后再挂 | 网络盘（NFS/iSCSI） |
| `defaults` | rw,suid,dev,exec,auto,nouser,async | 常规 |
| `bind` | 目录绑定挂载 | 容器/系统内部用途 |

> 记住 `nofail` ≠ `noauto`：前者"试着挂，挂不上也继续"，后者"根本不挂"。
> 云镜像中"数据盘自动挂载 + 不阻塞启动"的正确写法就是 `nofail`。

### 5.3 systemd 把 fstab 翻译成 mount 单元（为什么这些选项才生效）

systemd 生成器读 fstab，为每一条生成 `xxx.mount` 单元：

```
fstab: UUID=… /data xfs defaults,nofail,x-systemd.device-timeout=0 0 0
        ↓ systemd-fstab-generator
单元:   /data.mount  + 自动生成 dev-disk-by\x2duuid-…​.device 依赖
       nofail → 该依赖弱化为 Wants（而非 Requires）→ 挂不上不阻塞 boot
```

- 改了 fstab 后：`systemctl daemon-reload` 让单元重新生成
- 查看实际单元与依赖：`systemctl list-units --type=mount`、`systemctl status data.mount`
- 检查 fstab 是否有语法/设备问题：`systemd-analyze verify`、`findmnt --verify`
- 启动耗时归因：`systemd-analyze blame` / `critical-chain`

## 6. LVM：概念与云上为何被规范禁止

### 6.1 三层概念

```
物理卷 PV（/dev/vda3）
  └─ 卷组 VG（klas）           ← 把多个 PV 聚合成池
       └─ 逻辑卷 LV（root / backup）  ← 真正被格式化、挂载的对象
```

优点：弹性（在线扩/缩 LV、跨盘聚合、快照）。代价：多一层映射、多一层元数据与工具链。

### 6.2 云镜像规范禁 LVM 的技术原因

1. **`growpart` 打不穿**：扩容链路是"分区 → 文件系统"，中间多了 PV/LV 两层，需要 `pvresize` + `lvextend` + `xfs_growfs` 三步，cloud-init 的 `growpart`/`resizefs` 不会替你做完 → 用户开出来的实例根盘"扩了容量但 df 不变"
2. **规范要求根分区是物理分区且在末尾**（阿里云明文），LVM 违反此形态
3. 排查与救援复杂度上升（`rd.break` 里要激活 VG 才能看到根）
4. 数据盘/快照类操作（云侧）对 LVM 场景支持更弱

> 如果确实需要 LVM（如多盘聚合）：可以保留在数据盘上做，**系统盘保持物理分区**。

## 7. swap 为什么不要

- 云上内存可按需升配，swap 收益低
- swap 占用系统盘空间，且影响云盘快照/镜像体积
- 阿里云镜像规范明文禁止 swap 分区（`vm.swappiness=0` 出现在其 sysctl 建议中）
- 需要时可用 swapfile 或云监控告警替代

## 8. 挂载类故障定位与修复

| 现象 | 根因 | 处置 |
|---|---|---|
| 启动进 `emergency mode` | fstab 有条目挂不上（设备缺失/参数错） | 加 `nofail`；或先注释该条 |
| `Failed to mount /data` | 同上 | 同上 |
| 扩了云盘但 `df` 不变 | 只做了 host 侧扩容 | 执行 §4 的 ②③ 步 |
| 根分区扩不动 | 根不在末尾分区 | 重布局（或新建分区 + 数据迁移） |
| 设备名变了导致挂载错 | 用了 `/dev/vdX` 而非 UUID | 改 UUID |
| LVM 根救援时找不到 | VG 未激活 | initramfs shell 里 `vgchange -ay` |

**救援速记**（与启动链页一致）：GRUB `e` 加 `rd.break` → `mount -o remount,rw /sysroot` → `chroot /sysroot` → 改 fstab → `touch /.autorelabel`。

## 9. 动手清单（可丢弃 VM）

```bash
# ① 手工做一次云式布局（GPT + ESP + /boot + 根在末尾）
#    parted: mklabel gpt → mkpart ESP fat32 1MiB 601MiB → set 1 esp
#             mkpart boot xfs 601MiB 1.5GiB → mkpart root xfs 1.5GiB 100%
mkfs.vfat -F32 /dev/vda1; mkfs.xfs /dev/vda2; mkfs.xfs /dev/vda3

# ② 扩容链路演练（在正常运行的实例上）
growpart /dev/vda 3 && xfs_growfs / && df -hT /

# ③ 复现并修复"数据盘缺失阻塞启动"
#    fstab 加一条 UUID=不存在的盘 /data xfs defaults 0 0 → 重启进 emergency
#    改用 defaults,nofail,x-systemd.device-timeout=0 → 正常启动

# ④ 看 systemd 如何翻译 fstab
systemctl daemon-reload; systemctl list-units --type=mount
systemd-analyze blame | head

# ⑤ 观察 LVM 的扩容负担（理解规范为何禁它）
pvs; vgs; lvs
```
