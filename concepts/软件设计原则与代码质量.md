# 软件设计原则与代码质量

> 软件工程与架构入口。本文是「写对代码」的地基，下一篇 [[concepts/设计模式精讲]] 给可复用方案。

## 1. SOLID 五大原则

| 原则 | 全称 | 一句话 | 违反信号 |
|------|------|--------|---------|
| **S** | 单一职责 (SRP) | 一个类/函数只因一个理由变化 | 修改一处牵动多个无关需求 |
| **O** | 开闭 (OCP) | 对扩展开放、对修改封闭 | 加功能要改老代码 |
| **L** | 里氏替换 (LSP) | 子类可替换父类不破坏逻辑 | `Square` 继承 `Rectangle` 导致面积错误 |
| **I** | 接口隔离 (ISP) | 不依赖用不到的接口 | 实现类被迫实现空方法 |
| **D** | 依赖倒置 (DIP) | 依赖抽象而非具体实现 | 业务层直接 new 数据库驱动 |

**实战提示**：SOLID 是**权衡**不是教条。小脚本过度抽象反而拖累；大型长期演进系统里 SRP/DIP 收益最大。

## 2. 其他核心原则

- **DRY**（Don't Repeat Yourself）：重复逻辑抽公共函数/模块。但注意**巧合性重复**（两段代码相似但语义不同）不应强行合并——合并错比复制更糟。
- **KISS**（Keep It Simple）：优先最简单能工作的方案。
- **YAGNI**（You Aren't Gonna Need It）：不为臆想的未来需求加代码——对应 OCP 的「别提前抽象」。
- **编码向读倾斜**：代码被读的次数远大于写；命名与结构服务于读者。

## 3. Clean Code 核心

| 维度 | 好 | 坏 |
|------|----|----|
| 命名 | `calculateInvoiceTotal()` | `calc(a, b)` / `data1` |
| 函数 | 短、单职责、≤ 1 层抽象 | 200 行「上帝函数」 |
| 参数 | ≤ 3 个，多则用对象 | 8 个位置参数 |
| 错误 | 显式抛/返回，不吞异常 | `catch {}` 静默 |
| 注释 | 解释「为什么」 | 复述「做什么」的废话注释 |

> 注释记录**意图与约束**（为何这样写、边界条件），而非翻译代码。代码自解释时删注释。

## 4. 代码坏味道（Code Smells）

| 坏味道 | 表现 | 朝向 |
|--------|------|------|
| 重复代码 | 多处雷同 | 抽函数/模板方法 |
| 长函数 / 长类 | 一个单元干太多 | 拆小、单一职责 |
| 发散式变更 | 一个类因多需求改 | 拆类（SRP） |
| 霰弹式修改 | 一个需求改多处类 | 内聚到模块 |
| 特性依恋 | 函数狂调别的对象 | 搬近数据所在 |
| 过长参数列表 | 参数成堆 | 封装为参数对象 |
| 数据泥团 | 一组字段总一起传 | 抽值对象 |
| 注释过量 | 用注释补逻辑不清 | 重构让代码自明 |

详细消除手法见 [[entities/重构实战：识别并消除代码坏味道]]。

## 5. 质量不是「能跑」

```
可工作 (correct)
  → 可读 (readable)         ← Clean Code
  → 可测 (testable)         ← 依赖抽象、小函数
  → 可演进 (evolvable)      ← SOLID、低耦高内聚
  → 可观测 (observable)     ← 见 [[concepts/可观测性工程]]
```

## 6. 与架构的衔接

原则在**模块/类**层；放大到**服务/系统**层就是架构风格（[[concepts/架构风格演进]]）与分布式约束（[[concepts/分布式系统基础]]）。低层烂代码会放大高层复杂度——先写对，再谈架构。
