# 变更与配置管理

## 概述

软件项目最大的特征之一是**变更不可避免**。变更管理与配置管理共同构成项目治理的"闸门"。

## 变更管理

### 变更控制流程

1. **提交变更请求** — 描述变更内容、理由、影响
2. **初步评估** — PM 评估对范围/进度/成本/质量的影响
3. **CCB 审批** — 变更控制委员会决定批准/驳回/延期
4. **更新计划** — 批准后将变更纳入基准
5. **执行与验证** — 实施变更，确认效果
6. **记录归档** — 完整的变更日志

### 变更控制委员会（CCB）

- 典型成员：PM、PO、技术负责人、QA、客户代表
- 决策原则：**对项目整体目标的净影响**
- 日常小变更可授权 PO 或 PM 直接决策（敏捷中的 PO 权限）

## 配置管理

### 核心活动

1. **配置标识** — 将软件/文档识别为配置项（CI），分配唯一标识
2. **配置控制** — 对 CI 的变更受版本控制
3. **配置状态记录** — 记录每个 CI 的变更历史与当前版本
4. **配置审计** — 验证 CI 与需求/设计的一致性

### 配置项（CI）示例

- 需求规格说明书
- 架构设计文档
- 源代码（Git 仓库）
- 测试用例
- 部署脚本
- 配置文件模板

## 敏捷中的变更新模式

敏捷不排斥变更，而是**改变变更的时机**：
- Scrum：Sprint 内锁定范围，Sprint 间 PO 可重排 Backlog
- Kanban：随时可插入高优先级任务，WIP 限制防止过载
- 关键点：**缩短反馈周期**，使每次变更成本更低

## 工具支撑

- Git — 代码配置管理 + 分支策略
- Jira — Issue 工作流驱动变更审批
- Jenkins — CI/CD 自动化确保基线一致性
