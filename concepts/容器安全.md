# 容器安全（Container Security）

> 原理见 [[concepts/容器原理与运行时]]（Namespace/Cgroups 提供了「隔离视野 + 限额」，但**不是安全边界**）。本文讲如何把容器从「能跑」变成「跑得安全」。

---

## 1. 威胁模型：容器的安全边界在哪

容器**共享宿主机内核**。这意味着它和宿主机上其它进程、其它容器的隔离，靠的是内核的 Namespace/Cgroups——而这两者**设计目标是隔离，不是防护**。一旦内核有漏洞（或配置不当），容器内的进程就可能逃逸到宿主。

业界用 **4C 模型** 描述云原生安全层级（外层保护内层）：

```
Cloud（基础设施/云）  ─┐
Cluster（K8s 集群）    ─┤ 本文聚焦这两层里的「容器」部分
Container（容器镜像）  ─┤
Code（应用代码）       ─┘
```

主要攻击面：
| 攻击面 | 例子 |
|---|---|
| 镜像供应链 | 恶意基础镜像、依赖投毒、把密钥 `COPY` 进镜像 |
| 运行时逃逸 | 特权容器、挂载 `/var/run/docker.sock`、内核漏洞 |
| 权限提升 | 容器内 root + `cap SYS_ADMIN` + 可写宿主目录 |
| 横向移动 | 容器间无网络隔离、共享 ServiceAccount 令牌 |
| 资源滥用 | 无 cgroup 限额 → 邻居被饿死（Noisy Neighbor） |

> [!warning] 默认容器并非「沙箱」
> 一个不加任何限制的容器，运行在宿主内核上，一旦拿到 `CAP_SYS_ADMIN` 或挂载了宿主关键目录，就能影响整台机器。安全来自**主动加固**，不是容器天然自带。

---

## 2. 内核隔离的局限与真正边界

回顾原理篇三大基石的「安全含义」：

| 基石 | 是隔离？ | 是安全边界？ | 说明 |
|---|---|---|---|
| Namespace | ✅ 隔离视野 | ❌ 不是 | 不限制「能做什么」，只限制「能看到什么」；部分资源（内核 keyring、部分设备）仍共享 |
| Cgroups | ✅ 限制用量 | ❌ 不是 | 防 DoS/资源挤占，但不防提权 |
| OverlayFS | ✅ 隔离文件视图 | ⚠️ 部分 | 防写坏宿主，但默认 upper 在宿主磁盘上 |

**真正的安全边界靠这三层**：
1. **Capabilities / seccomp / MAC** —— 限制「进程能对内核做什么」。
2. **Rootless + User Namespace** —— 把容器内 root 变成宿主上的「nobody」。
3. **供应链 + 运行时策略** —— 保证「跑的东西可信」且「行为受控」。

---

## 3. Linux Capabilities（降权核心）

在传统 Unix 里 `root` 拥有一切权限。Linux 把 root 权限拆成 **~40 个 capability**（如 `CAP_NET_BIND_SERVICE` 绑低位端口、`CAP_SYS_ADMIN` 干几乎一切）。容器默认只被授予其中约 15 个，但**仍可能过多**。

> [!tip] 黄金法则：drop all，只加需要的
> 绝大多数应用不需要任何特权能力。

```bash
# docker：先全部回收，再按需放开
docker run --cap-drop ALL --cap-add NET_BIND_SERVICE myapp
# 禁止提权（即使有漏洞也不能通过 setuid 变 root）
docker run --security-opt no-new-privileges myapp
```

K8s 等价（见第 9 节模板）：
```yaml
securityContext:
  capabilities:
    drop: ["ALL"]
    add: ["NET_BIND_SERVICE"]
  allowPrivilegeEscalation: false
```

## 4. Seccomp（过滤系统调用）

即便给了 capability，进程能调用的**系统调用**仍有几百个，绝大多数用不到。seccomp 在内核层面**按 syscall 名白/黑名单过滤**，直接缩小内核攻击面（很多容器逃逸利用的是冷门 syscall，如 `ptrace`、`mount`、`bpf`）。

- **默认 profile**：Docker/containerd 自带 `default.json`，禁掉约 44 个危险 syscall。
- **自定义**：用 `seccomp` 生成工具（`docker run --security-opt seccomp=/path/profile.json`）。

```bash
# 开启默认 seccomp（多数运行时默认已开，显式指定更稳）
docker run --security-opt seccomp=default.json myapp
# 生成一个只放行应用实际用到 syscall 的严格 profile
# 思路：strace/uber 的 go-secdump 记录运行时 syscalls → 收敛成白名单
```

> [!note] 与原理篇呼应
> `runc` 在启动容器时通过 **seccomp 过滤器（libseccomp）** 装载这些规则——这正是「运行时栈」里低层运行时做的安全动作之一。

---

## 5. MAC：AppArmor / SELinux

Capabilities/seccomp 管「能调哪个 syscall」，**MAC（强制访问控制）** 管「进程能访问哪个文件/端口/能力」，由内核 LSM 强制执行。

| 机制 | 主流平台 | 作用 |
|---|---|---|
| **AppArmor** | Ubuntu/Debian/Suse | 给进程绑定 profile，限制其能读/写/执行的文件路径与网络 |
| **SELinux** | RHEL/CentOS/Rocky | 基于标签的强制访问控制，更细但配置更重 |

```bash
# docker 指定 AppArmor profile
docker run --security-opt apparmor=docker-default myapp
# SELinux：挂卷时加 :z（共享）或 :Z（私有）标签，否则容器可能读不到
docker run -v /data:/data:Z myapp
```

K8s：`pod.spec.securityContext.seLinuxOptions { level: "s0:c123,c456" }` 做多租户隔离。

## 6. Rootless 与 User Namespace（根本降权）

前面都是「在容器内 root 的前提下收权限」。**Rootless** 更进一步：容器内 `root` 被 **User Namespace** 映射成宿主上的**普通非特权用户**（如 uid 100999），即使逃逸成功，在宿主看来也只是个普通用户，拿不到宿主 root。

```bash
# 以 rootless 模式跑 containerd/docker（用户级守护进程，无需 root 启动）
dockerd-rootless-setuptool.sh install
# 或 podman（天生 rootless 优先）
podman run --userns=auto myapp
```

优势：
- 容器内 `uid 0` ≠ 宿主 `uid 0`，逃逸危害大幅降低。
- 无需特权守护进程，缩小攻击面。

> [!caution] rootless 的限制
> 部分功能受限：某些网络模式（`macvlan`）、需要特权 syscall 的场景、较老内核。生产落地需评估。

## 7. 镜像供应链安全

「跑的东西可信」是第一道关。

| 措施 | 做法 |
|---|---|
| 最小基础镜像 | `alpine` / `distroless` / `scratch`，减少预装软件与 CVE |
| 非 root 用户 | Dockerfile 里 `USER nonroot`，避免容器内默认 root |
| 漏洞扫描 | `trivy` / `grype` 扫镜像，CI 门禁拦截高危 |
| SBOM | 生成软件物料清单（`syft`/`trivy sbom`），便于溯源 |
| 镜像签名 | `cosign`（Sigstore）/ Notary v2 对镜像 digest 签名 |
| 来源校验 | 仓库只允许来自可信 CI 推送；K8s 准入校验签名（见第 8 节） |
| 密钥不入镜像 | 用 Secret/外部密钥管理（[[concepts/Kubernetes 核心架构与组件]]），禁止 `COPY .env` |

```bash
# 生成 SBOM + 扫描
syft myapp:1.2.3 -o json > sbom.json
trivy image myapp:1.2.3

# 用 cosign 签名并验签
cosign sign --key cosign.key registry.example.com/myapp:1.2.3
cosign verify --key cosign.pub registry.example.com/myapp:1.2.3
```

> 镜像加密/签名可结合 [[entities/国密 SM2_SM3_SM4 实战]] 的 SM2 体系做国密合规签名方案。

## 8. 运行时安全与准入控制

镜像再干净，运行时配置不当仍可被攻破。关键是**默认拒绝危险配置**。

### 8.1 危险配置清单（必须禁止）

| 配置 | 风险 | 加固 |
|---|---|---|
| `privileged: true` | 等同宿主 root，可直接逃逸 | 禁止；确需设备用 `cap-add` 精确给 |
| 挂载 `/var/run/docker.sock` | 拿到宿主机 docker 控制权 | 禁止 |
| `hostPID` / `hostNetwork` | 看到宿主进程/网络，横向威胁 | 默认关 |
| `allowPrivilegeEscalation: true` | setuid 提权 | 设 `false` + `no-new-privileges` |
| 可写根文件系统 | 被写入恶意程序 | `readOnlyRootFilesystem: true`，临时目录挂 `emptyDir` |

### 8.2 PodSecurity Admission（K8s 内置）

K8s 1.25+ 用 **Pod Security Admission** 给 Namespace 设三级标准：

| 级别 | 要求 |
|---|---|
| `Privileged` | 无限制（仅系统组件用） |
| `Baseline` | 禁已知危险（privileged/host 挂载等） |
| `Restricted` | 最严：禁提权、drop ALL caps、rootless、只读根、seccomp default |

```bash
kubectl label ns prod pod-security.kubernetes.io/enforce=restricted
```

### 8.3 运行时入侵检测：Falco

Falco 用 **eBPF**（见 [[concepts/eBPF 核心架构]]）在内核层监控异常行为，规则匹配即告警/拦截：

```yaml
# 例：检测容器内启动 shell（常被用作横向移动信号）
- rule: Terminal shell in container
  desc: 容器内出现交互式 shell
  condition: container.id != host and proc.name in (bash, sh, zsh)
  output: "Shell 在容器内启动 (user=%user.name)"
```

> 配合 [[concepts/可观测性工程]] 把 Falco 告警接入 Prometheus/Alertmanager。

## 9. 安全配置速查模板（K8s securityContext）

直接可复用的「Restricted」级 Pod 安全基线：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: hardened
spec:
  securityContext:                 # Pod 级
    runAsNonRoot: true
    runAsUser: 1000
    seccompProfile:
      type: RuntimeDefault         # 启用默认 seccomp
  containers:
  - name: app
    image: registry.example.com/myapp:1.2.3@sha256:...   # 用 digest 固定，防篡改
    securityContext:               # 容器级
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities:
        drop: ["ALL"]
    resources:                     # cgroups 限额（防资源滥用）
      requests: { cpu: "100m", memory: "128Mi" }
      limits:   { cpu: "500m", memory: "256Mi" }
    volumeMounts:
    - { name: tmp, mountPath: /tmp }
  volumes:
  - name: tmp
    emptyDir: {}
```

## 10. 网络与密钥（衔接分布式安全）

- **网络最小暴露**：用 NetworkPolicy / Cilium 默认拒绝、按需放行（[[entities/Cilium 容器网络]]、[[concepts/Kubernetes 网络模型]]）。
- **密钥不离线泄露**：Secret 经 KMS 加密存 etcd（[[concepts/Kubernetes 核心架构与组件]] 的 etcd 加密），生产用 Vault 等外部密钥管理动态注入。
- **服务身份**：用 mTLS（Service Mesh / SPIFFE）做工作负载身份认证，防横向伪造。
