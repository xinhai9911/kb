# 磁盘加密 与 软RAID 的 镜像 约束

> 相关：[[concepts/磁盘分区 文件系统 与 挂载管理]]（分区与挂载）、[[concepts/initramfs 与 dracut]]（加密根的启动依赖）、
> [[concepts/云平台 镜像 与 云盘 产品语义]]（云盘类型与镜像生命周期）。

## 1. 先分清两层加密（这是最常见的混淆）

| 层次 | 谁实现 | 密钥谁管 | 对镜像的影响 |
|---|---|---|---|
| **平台侧云盘加密** | 云平台（对 guest **透明**） | 云侧 KMS / 平台托管 | 镜像**不需要任何改动**；guest 内看到的是明文盘 |
| **guest 侧 LUKS / dm-crypt** | 镜像内（系统自己） | 你自己（密码 / keyfile / 网络解锁） | **镜像必须改造**：initramfs 要带解密能力、启动时要能自动解锁 |

两者可以**叠加**（平台加密 + 镜像内 LUKS），但收益有限、复杂度翻倍 —— 除非合规强制，一般**二选一**。

## 2. guest 侧 LUKS：对镜像提出的四个要求

### 2.1 initramfs 必须能解密

加密根（或加密的 `/` 所在的 LV）意味着内核启动后**必须先解开密码层才能挂根**：

```
内核 → initramfs → 需要 cryptsetup 能力打开 LUKS → 得到明文的 root 映射 →
     按 root=UUID（指向映射后的设备）挂根
```

对应要点：

| 项 | 说明 |
|---|---|
| `cryptsetup` / `dm-crypt` 模块进 initramfs | RHEL 系用 dracut 的 `crypt` 模块（通常会自动带入，但要验证） |
| 内核参数 | `rd.luks.uuid=<LUKS UUID>`（RHEL 系）或 `cryptdevice=`（Debian 系）；`rd.luks.key=` 指定 keyfile |
| **root= 的指向变了** | 指向**映射后**的 `/dev/mapper/xxx`（或对应 UUID），不再是物理分区 —— 这与"全链路 UUID 化"的规则要一起重新核对 |
| 验证手段 | `lsinitrd \| grep -E 'crypt|cryptsetup'`；`grubby --info=ALL` 看内核参数 |

> 与 [[concepts/initramfs 与 dracut]] §7 的故障模式**叠加**：加密场景下"打不开 LUKS"和"找不到根盘"表现相似（都卡在 initramfs），排障要先用 `rd.shell` 看清是"设备没出现"还是"LUKS 没解开"。

### 2.2 自动解锁：云上不能靠人工输入口令

无人值守的实例必须能自己解锁，常见三条路：

| 方式 | 机制 | 代价 / 风险 |
|---|---|---|
| **NBDE（Tang/Clevis）** | 启动时向网络上的 Tang 服务取钥（有阈值可多 Tang） | 依赖网络可达（需要 initramfs 网络 + 早期 DNS/IP）；Tang 挂了就起不来 |
| **keyfile 放本地（如 ESP）** | 显然不安全：密钥与密文同盘 → 只防"盘被单独带走" | 云上意义有限（盘在云里） |
| 仅人工输入 | VNC/串口输入口令 | 不适合无人值守；仅适合"极高安全 + 人工介入"场景 |

> 判断标准：**如果你的威胁模型是"云平台/运维能看到盘内容"，那平台侧加密已经解决；**
> **如果是"磁盘镜像可能被导出带走"，才值得上 LUKS** —— 但要在 keyfile/NBDE 的运维代价上算账。

### 2.3 对云侧救援与运维的约束（最容易被忽略）

| 场景 | 加密前 | 加密后 |
|---|---|---|
| 挂盘到另一实例修 | 直接挂载 | **需要先解密**（另一实例要有密钥），流程复杂 |
| 云侧控制台的救援模式 | 可用 | 常因无法解密而**失效** |
| 快照 / 镜像制作 | 直接做 | 平台做的是**密文盘**的快照（仍可用，但离线分析要密钥） |
| 重置密码类操作 | 离线改 shadow | 需要先解密盘 |
| 合规审计取证 | 直接读 | 需要密钥交付流程 |

> 结论：**加密会把"云上最常用的排障手段"变成需要额外步骤的操作**。上加密前先确认你的团队/客户有没有配套的密钥管理与解密流程。

## 3. mdadm 软 RAID：与云盘语义的冲突

### 3.1 云盘的"多副本"已经在平台侧了

主流云的云盘本身就是**多副本/三副本**存储。因此：

| 方案 | 收益 | 代价 |
|---|---|---|
| 再叠 **RAID1**（两块云盘镜像） | 冗余——但冗余已在平台侧，**收益很低** | 成本翻倍、写放大、复杂度 |
| **RAID0**（两块云盘条带） | 吞吐/IOPS 提升 | **故障域放大**（任一块坏即全丢）；且不如直接选更高档位云盘 |
| **RAID10** | 吞吐 + 冗余 | 成本与复杂度双高 |

> 更优选择通常是：**升级云盘档位（ESSD PL2/PL3 等）而不是做 RAID0** —— 见 [[concepts/云平台 镜像 与 云盘 产品语义]] §3。

### 3.2 系统盘**不应**做软 RAID（与镜像直接相关）

| 原因 | 说明 |
|---|---|
| 启动依赖 | 软 RAID 需要在 initramfs 阶段组装阵列（`mdadm` 进 initramfs + `rd.md.uuid=` 等参数）—— 链路更长、更容易起不来 |
| 云平台不认识 | 平台按"一个系统盘 = 一个块设备"管理；镜像/快照/扩容链路都为单盘设计 |
| 扩容链路断掉 | `growpart` 与文件系统扩容假设单盘布局；RAID 下要改走更复杂路径 |
| 与加密叠加 | RAID + LUKS 同时上，initramfs 依赖将进一步交织 |

**数据盘**上做软 RAID 是可行的（不涉及引导），但先算清"平台多副本 + 更高档位"能不能替代它。

## 4. 结论性建议（可直接作为评审口径）

| 需求 | 推荐做法 | 不推荐 |
|---|---|---|
| 满足"数据加密"合规项 | **平台侧云盘加密**（对镜像零改造） | 无必要在镜像里做 LUKS |
| 防止镜像/磁盘被导出后泄露 | 镜像内 LUKS + **NBDE（Tang）** 或严格的人工解锁流程 | keyfile 与密文同盘 |
| 提升数据盘吞吐/IOPS | 提高云盘档位 | 用 RAID0 拼盘 |
| 数据盘冗余 | 靠平台多副本 + 快照/备份策略 | 叠 RAID1 |
| 系统盘 RAID/加密 | 不做 RAID；加密仅在有明确威胁模型时做 | 两者同时上 |
| 加固/等保要求的"加密存储" | 先核对条款到底要求**平台加密**还是**guest 内加密** | 默认按最重的方案上，徒增运维成本 |

## 5. 检查清单

```
□ 明确加密层次：平台侧（透明）还是 guest 内 LUKS（需改造）
□ 若 LUKS：initramfs 含 cryptsetup/dm-crypt；rd.luks.* 参数已配；root= 指向映射设备
□ 若 LUKS：自动解锁方案已定（NBDE/keyfile/人工）并有可用性评估
□ 若 LUKS：救援与取证流程已更新（挂盘修复、控制台救援、快照分析）
□ 系统盘未做软 RAID
□ 数据盘若做 RAID：已与"更高档位云盘"做过成本/性能对比
□ 加密/RAID 组合场景已在本地 qemu 与云上各实测一次启动
□ 相关依赖（加密参数、mdadm）已纳入镜像台账与变更记录
```
