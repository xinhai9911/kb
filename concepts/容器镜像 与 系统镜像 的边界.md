# 容器镜像 与 系统镜像 的边界

> 前置：[[concepts/容器原理与运行时]]、[[entities/容器打包与管理]]。
> 相关：[[concepts/KVM 公有云 镜像 适配]]（系统镜像侧）、[[concepts/Linux 启动链 与 引导]]（为什么系统镜像需要引导链）。

## 1. 一个词，两个世界

| 维度 | **OCI 容器镜像** | **系统镜像** |
|---|---|---|
| 载体 | 分层 tar 层 + `config.json` + manifest | 磁盘镜像（raw/qcow2/vhd） |
| 内容边界 | 应用 + 依赖 + 部分用户空间；**通常不含内核** | 分区表 + 引导器 + 内核 + initramfs + rootfs |
| 内核 | **共享宿主机内核** | **自带内核** |
| 启动方式 | 容器运行时（containerd/docker）创建 namespace 起进程 | 固件 → 引导器 → 内核 → initramfs → systemd |
| 隔离粒度 | 进程级（namespaces/cgroups） | 硬件级（虚拟机） |
| "分层"含义 | 文件系统层叠加（copy-on-write） | 分区/挂载点分层（ESP//boot//），与镜像格式无关 |
| 分发通道 | registry（push/pull，按层增量） | 对象存储（OSS/OBS/COS）上传并"导入" |
| 变更成本 | 秒级（换层、重启 Pod） | 分钟级（导出、上传、导入、建实例） |

**最容易踩的认知混淆**：两个都叫"分层"，但**维度不同**——
容器是"文件系统层"，系统镜像是"磁盘/分区结构"。所以"容器镜像能不能直接当系统镜像用"的答案是：
**一般情况下不能**（没有引导链、没有内核、没有分区结构）。

## 2. 为什么不能互相替代（具体缺什么）

### 2.1 容器镜像 → 系统镜像：缺的东西

| 缺什么 | 后果 |
|---|---|
| 引导链（ESP + GRUB + shim） | 无引导代码，云平台导入后起不来 |
| 内核 + initramfs（通常） | 无法独立启动（要共享宿主内核） |
| 分区表与文件系统布局 | 云平台按"磁盘"解析镜像，找不到可引导结构 |
| 系统服务与 init（systemd PID 1） | 容器里通常只有单个应用进程 |
| cloud-init / agent | 无实例初始化能力 |

可用的桥接手段（**合法且常用**）：把容器 rootfs（`docker export` / `buildah mount`）作为**素材**，
配合发行版工具补引导与内核后打包成磁盘镜像。本质是"用容器构建系统镜像"，不是"直接当系统镜像用"。

### 2.2 系统镜像 → 容器镜像：反向也不成立

系统镜像带内核、引导、设备节点与大量系统服务，塞进容器会：
- 体积巨大（几十 GiB）
- 与宿主内核/命名空间冲突（`systemd` 在容器里要特权重启、`/sys`、`/proc` 语义不同）
- 失去容器化的意义（快速分发、按层增量、秒级启动）

## 3. 决策表：这个场景该交付哪一种

| 场景 | 交付形态 | 理由 |
|---|---|---|
| 业务应用上云（微服务、Web、任务） | **容器镜像** | 弹性、快速发布、与 K8s 天然契合 |
| 交付整机/一体化 appliance（本库 DOM 镜像场景） | **系统镜像** | 需要完整内核与硬件/数据面控制权 |
| 网络数据面（DPDK/VPP，需大页、绑核、专用网卡） | **系统镜像** | 需要内核参数、大页预留、驱动控制（见 [[entities/高性能 场景 云上镜像 配置]]） |
| 安全 appliance / 需要系统级加固与审计 | **系统镜像** | 需要 SELinux 策略、内核参数、启动链控制（见 [[concepts/SELinux 与 镜像制作]]） |
| 边缘设备（非 KVM、要装机到硬件） | **系统镜像**（+ 烧录流程） | 无容器运行时可用 |
| 想两者兼得 | **新范式**（§4）或"容器交付 + 系统镜像兜底"双轨 | 权衡交付复杂度 |

## 4. 新范式：不可变系统 / 以容器镜像格式分发系统

一批现代发行版把"系统"也做成了镜像化交付（**bootc / rpm-ostree / 不可变系统**）：

```
容器 registry 里存放"系统镜像"（含内核/引导/rootfs 的 OCI 镜像）
        ↓ 在实例或构建机上
   转成磁盘镜像 / 事务化更新到已装系统（bootc install / ostree deploy）
        ↓
   实例启动后系统分区是只读 + 可原子回滚
```

| 代表 | 特点 |
|---|---|
| Fedora CoreOS / Flatcar / Talos Linux | 不可变 rootfs + 原子升级，Talos 甚至把整个 OS 当 API 管理 |
| bootc（bootable containers） | **用 OCI 镜像作为系统镜像来源**，`bootc install` 落到磁盘 |
| rpm-ostree | 事务化、可回滚的系统更新 |

**注意边界**：这类系统**生成物仍然是磁盘镜像/磁盘上的系统**（要引导链、要固件），
只是**构建与分发通道**借用了容器那套（registry、分层、签名）。
"容器镜像 ≠ 能启动的 VM"这条边界依然成立。

## 5. 两者在 CI/CD 里的分工

```
代码变更
 ├─ 应用链路：构建 OCI 镜像 → push registry → K8s 滚动更新        （分钟级）
 └─ 平台链路：构建系统镜像 → 离线改造/清理 → 自检 → 导入云平台 → 建实例验收   （小时级）
```

| 关注点 | 容器链路 | 系统镜像链路 |
|---|---|---|
| 版本与回滚 | tag/digest + 滚动更新 | 镜像版本 + 快照 + 重建实例 |
| 安全扫描 | 镜像层扫描（Trivy 等） | 系统级基线扫描 + SELinux/加固（见 [[concepts/SELinux 与 镜像制作]]） |
| 体积优化 | 分层缓存、多阶段构建 | 清日志/清身份/稀疏化（见 [[entities/镜像格式 与 离线处理工具链]]） |
| 门禁 | 镜像准入（admission） | 镜像自检（`projects/kvm-image-check`） |

## 6. 常见误区

| 误区 | 纠正 |
|---|---|
| "把 rootfs 打成 tar 就是系统镜像" | 缺引导链与内核，云平台起不来 |
| "容器里能跑 systemd，所以能当 VM 用" | 容器的 systemd 仍共享宿主内核，不解决引导与硬件控制 |
| "镜像分层越少越好" | 系统镜像的"层"是分区结构，谈的是布局（ESP//boot// 根在末尾），不是层数 |
| "bootc 就是容器镜像当 VM" | 它是"容器镜像格式作为系统来源"，最终仍需落成可引导磁盘 |
| "系统镜像也能秒级发布" | 分发通道是对象存储 + 导入，天然比 registry 慢 |
