# 架构风格演进

> 架构是「把系统切成什么、怎么连」。本文横向对比主流风格与取舍。分布式细节见 [[concepts/分布式系统基础]]。

## 1. 演进主线

```
单体 (Monolith)
  └─ 分层 (Presentation/Service/DAO)        ← 解耦「层」
       └─ 模块化单体 (Module Monolith)       ← 解耦「模块」，仍单部署
            └─ SOA (企业总线)                 ← 跨组织服务
                 └─ 微服务 (Microservices)   ← 小团队自治、独立部署
                      ├─ 事件驱动 (Event-Driven)
                      ├─ CQRS + Event Sourcing
                      └─ Serverless / FaaS
```

规律：**耦合点不断从「代码内」推到「网络/契约」**。代价是分布式复杂度上升。

## 2. 单体 vs 微服务（核心权衡）

| 维度 | 单体 | 微服务 |
|------|------|--------|
| 部署 | 一次发布全部 | 每服务独立发布 |
| 伸缩 | 整体复制 | 按热点服务独立扩 |
| 故障隔离 | 一个 bug 拖垮全部 | 一服务挂不影响其余 |
| 数据 | 单库、强一致易 | 每服私有库、需最终一致 |
| 运维/链路 | 简单 | 需服务发现/可观测/熔断 |
| 团队 | 小团队够用 | 多团队并行（康威定律） |
| 延迟 | 进程内调用 | 网络跳数 + 序列化 |

> 经验法则：**不到 2–3 个团队别上微服务**。多数中型系统用「模块化单体 + 清晰模块边界」更划算，需要时才拆。

## 3. 分层架构

```
Presentation ──► Service ──► Domain ──► DAO ──► DB
```
- 强制依赖方向向下，避免循环依赖（见 [[concepts/软件设计原则与代码质量\|DIP]]）。
- 常见腐化：Service 层互相调用成网、DAO 被 Presentation 直接访问。

## 4. 事件驱动架构（EDA）

```
服务A ──事件──► 消息总线(Kafka/Pulsar) ──► 服务B/C 各自消费
```
- 优点：解耦、异步、削峰、天然审计（事件日志）。
- 缺点：最终一致难调试、消息乱序/重复需处理（幂等，见 [[concepts/分布式系统基础]]）。
- 常与微服务结合：命令用同步（gRPC/REST），结果用事件广播。
- 消息总线落地见 [[concepts/Kafka 消息队列与流处理]]（分区/副本/Exactly-once/与 Pulsar 对比）。

## 5. CQRS 与 Event Sourcing

- **CQRS**：读写模型分离——写路径（命令）走领域模型，读路径（查询）走专用视图/投影。解决「同一模型既要支持复杂写又要支持高并发读」的冲突。
- **Event Sourcing**：状态不存当前值，存「事件序列」；当前状态 = 重放事件。天然审计、可回放、时间旅行调试；代价是查询需建投影、学习曲线陡。
- 二者常一起用（ES 产生事件 → CQRS 读侧投影），但不是银弹——简单 CRUD 别上。

## 6. Serverless / FaaS

- 按请求伸缩到零、按用量计费；适合突发/事件触发负载。
- 缺点：冷启动延迟、厂商锁定、长任务/有状态不便、调试难。
- 常见于胶水逻辑、文件处理、Webhook。

## 7. 整洁架构 / 六边形（依赖向内）

```
                 ┌───────────────┐
   外部适配器 ──► │  Use Cases     │ ◄── 依赖倒置：外层依赖内层抽象
                 │  (应用业务)    │
                 │  Entities      │
                 └───────────────┘
```
- 核心域模型不依赖框架/DB/Web；所有 I/O 走端口（接口）注入。
- 好处：可测、可换基础设施（换 DB/框架不动业务）。对应 [[concepts/软件设计原则与代码质量\|DIP]] 放大到架构层。

## 8. 演进式架构

- 架构不是一次定死，而是**可演进**：用契约测试、防腐层（ACL）、绞杀者模式逐步替换老系统。
- 技术债（[[concepts/系统设计思维\|技术债管理]]）要持续还，避免大爆炸重写。
