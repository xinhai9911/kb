# 系统设计思维

> 前面是「具体知识」，本文是「怎么思考」。系统设计的本质是**在约束下做权衡**。

## 1. Trade-off 是第一性原理

没有「最好」的架构，只有「在当前约束下最合适」的：

```
约束：团队规模 / 工期 / 流量 / 预算 / 合规 / 既有系统
            │
            ▼
   方案空间（单体↔微服务、SQL↔NoSQL、CP↔AP…）
            │
            ▼
   选一个并清楚放弃什么
```

> 每选一个方案，都要能说出**放弃了什么**。说不出 = 没想清。

## 2. 非功能需求优先排序

功能需求人人会写，决定系统成败的是**非功能需求（NFR）**：性能、可用性、安全、可维护性、成本。先问：

- 目标 SLA 是多少（99.9%？99.99%）？→ 决定冗余/多活。
- 峰值 QPS 与数据量？→ 决定容量/分片。
- 合规要求？→ 决定加密/审计（[[concepts/加密算法总览与分类]]）。

## 3. 容量规划与长尾

- **平均延迟骗人**：用户感知的是 P95/P99（[[concepts/可观测性工程]] §3）。
- 容量估算：QPS × 单次资源 ≈ 总需求；留 **headroom（余量 30–50%）** 应对突发。
- 长尾来源：GC、锁竞争、慢查询、网络抖动、尾部服务。用分位数 + 追踪定位。

## 4. 经典权衡

| 权衡 | 一端 | 另一端 |
|------|------|--------|
| 延迟 vs 吞吐 | 同步低延迟 | 批量高吞吐 |
| 一致 vs 可用 | CP（[[concepts/分布式系统基础]]） | AP |
| 简单 vs 灵活 | 单体 | 微服务 |
| 成本 vs 冗余 | 单副本 | 多活 |
| 实时 vs 解耦 | 同步调用 | 事件异步 |

## 5. 演化式架构

- 别试图一次设计完美。先满足当前，留**演进通道**：清晰模块边界、契约测试（[[concepts/CI_CD与测试策略]]）、防腐层（[[concepts/领域驱动设计 DDD]]）。
- 用**绞杀者模式**逐步替换，而非大爆炸重写。

## 6. 技术债管理

- 技术债 = 为速度故意/无意欠下的维护性代价。
- 关键：债要**可见、可量化、定期还**。用可观测指标（构建时间、缺陷率、改一处波及面）衡量。
- 不还不爆，但还太勤拖慢业务——按利息（影响）排优先级。

## 7. 用数据决策，别用喜好

- 争议时上**基准测试 / A-B / SLO 数据**（[[concepts/可观测性工程]] §5），而非「我以前用过」。
- 架构评审记录：决策 + 理由 + 被放弃的替代方案。未来的人（包括你）会感谢。
