# 内核热补丁 与 镜像 更新 策略

> 前置：[[concepts/镜像 资产 治理 与 成本]]（更新策略四选一的位置）、[[concepts/Linux 启动链 与 引导]]（内核在启动链中的位置）。
> 产线：[[entities/镜像 构建 流水线]]（重建镜像主干）。

## 1. 问题域：CVE 应急 vs 可复现

系统镜像的常规更新是"重建镜像 → 换实例"，周期是**小时级**。
但高危 CVE 的窗口可能是**小时**。两者之间需要一个"不重启就修掉"的手段——这就是热补丁的位置。

| 维度 | 热补丁 | 重建镜像 |
|---|---|---|
| 生效时间 | 分钟级（加载模块） | 小时级（构建/导入/重建实例） |
| 是否需要重启 | 否 | 是（或至少重建实例） |
| 覆盖能力 | **有限**（见 §3） | 完整 |
| 可复现性 | 低（实例状态被就地改写） | 高（镜像即事实） |
| 定位 | **止血** | **根治** |

> 一句话原则：**热补丁用于争取时间，镜像重建负责最终收敛。**
> 只打热补丁不收敛 = 把技术债滚成雪球（新扩容的实例仍然带 CVE）。

## 2. 机制：不停机替换内核函数

内核主线自 4.x 起提供 **livepatch 框架**（`CONFIG_LIVEPATCH`），各发行版封装成不同工具：

| 发行版生态 | 工具 | 备注 |
|---|---|---|
| RHEL / CentOS 系 | **kpatch**（+ 发行版提供的 `kpatch-patch-*` 包） | 需内核支持 livepatch；补丁按内核版本流分发 |
| Ubuntu | **Canonical Livepatch**（`livepatch`/`canonical-livepatch` 客户端） | 与企业订阅绑定的服务化形态 |
| SUSE | **kGraft** 血统的 livepatch 实现 | per-task 一致性模型 |

**核心思路**（以 kpatch 类实现为例）：

```
① 用"打了补丁的内核"与"原内核"的编译产物做 diff，提取被改动函数的二进制
② 打包成一个内核模块（.ko）
③ 加载模块 → 通过 ftrace/fentry hook 把旧函数的调用重定向到新函数
④ 一致性保证：确保所有 CPU/任务都不再执行旧函数（否则会"半旧半新"）
```

- **函数级替换**：被改的是**函数**，不是任意代码
- **一致性模型**：实现上靠 ftrace hook + 一致性检查（或 stop_machine 类手段）保证切换瞬间无人在旧函数里
- **累积加载**：多个补丁可叠加，但有顺序与依赖约束

## 3. 能力边界（决定"能不能用它救急"）

| 限制 | 说明 | 后果 |
|---|---|---|
| **只能改函数** | 无法改数据结构布局、静态数据、被 inline 掉的代码 | **很多安全补丁改的是结构体/字段 → 无法热修** |
| **与内核版本 + 编译配置强绑定** | 补丁必须针对**精确的内核版本与配置**构建 | 自研/自编译内核基本拿不到现成补丁，要自己 build |
| 内联与编译器优化 | 被内联的函数无独立二进制 → 无法 hook | 部分路径修不掉 |
| 一致性/时序 | 初始化路径、早期代码、某些锁上下文不安全 | 需逐补丁评估 |
| 累积复杂度 | 补丁栈越长，冲突与验证成本越高 | 长期只靠热补丁不可维护 |

> 结论：**热补丁的 CVE 覆盖是"部分覆盖"**。真正的高危数据结构类缺陷（如越界、竞态改结构）通常只能重启修
> —— 这也解释了为什么所有发行版都把热补丁定位成"过渡手段"而不是长期方案。

## 4. 云上与容器场景的适用性

| 场景 | 适用性 | 说明 |
|---|---|---|
| 公有云 VM（自有镜像） | 可用，但**责任在你** | 云厂商只负责宿主与公共镜像；你的自定义内核补丁要自己出、自己发 |
| 云厂商公共镜像 | 无需你做 | 厂商维护其内核补丁流 |
| 宿主机 / K8s 节点 | **收益最大** | 补丁打在宿主内核 → 所有共享该内核的容器/租户一起受益，无需重启 Pod |
| 不可变系统（bootc/ostree） | 通常不用热补丁 | 事务更新 + 原子回滚更快更干净（见 [[concepts/容器镜像 与 系统镜像 的边界]] §4） |
| 安全 appliance（本库场景） | **需谨慎** | 等保/合规常要求"修复可验证"，热补丁状态必须可查、可审计（§7） |

**云上特有的三个坑**：

1. **镜像里不带补丁** → 新扩容的实例仍然有洞（热补丁没有改变镜像内容）
2. **自编译内核** → 拿不到发行版补丁，得自己具备 `kpatch-build` 之类的构建能力与符号
3. **补丁也需要分发通道** → 你是自建仓库还是跟着发行版走？这本身要进镜像治理

## 5. 支持热补丁需要在镜像里预置什么

| 项 | 用途 |
|---|---|
| 内核开启 livepatch 支持 | 前提（`CONFIG_LIVEPATCH`；发行版内核一般已开） |
| `kpatch` / livepatch 客户端工具 | 加载、查询、卸载补丁 |
| 补丁构建环境（若需自建补丁） | `kpatch-build` + 内核源码/调试信息 → **建议放在构建机，不放镜像** |
| 补丁分发与仓库 | 内网仓库/对象存储 + 校验；纳入镜像资产治理 |
| 查询脚本 | 把补丁状态纳入巡检（§6） |

> 注意：**"能热补丁"不等于"该热补丁"**。把补丁工具装进镜像意味着你承诺维护这条通道，
> 要有配套的测试与回滚预案，否则出问题时比不打补丁更糟。

## 6. 验证与回滚

```bash
# 是否已加载/生效（不同实现命令不同，三选一看环境）
kpatch list
cat /sys/kernel/livepatch/*/enabled 2>/dev/null
canonical-livepatch status 2>/dev/null

# 模块层面确认
ls /sys/module/ | grep -i -E 'kpatch|livepatch'
dmesg | grep -i -E 'livepatch|kpatch'
```

| 动作 | 手段 |
|---|---|
| 灰度验证 | 先在少量实例加载，观察 dmesg/业务指标，再全量 |
| 回滚 | 卸载补丁模块（`kpatch unload` / 禁用对应 livepatch 项）→ 回到未修补状态（注意：**回滚是"回到有洞"**） |
| 审计留痕 | 记录：补丁 ID ↔ CVE ↔ 内核版本 ↔ 加载时间 ↔ 实例清单 |

## 7. 与镜像治理、审计的衔接（关键接点）

**"待收敛清单"**：每打一次热补丁，就产生一条债务

```
热补丁 ID / CVE / 目标内核版本 / 影响实例集合
    → 待收敛镜像版本：appliance-x.y.z+n（计划日期）
    → 收敛判据：新镜像里 CONFIG/源码已含该修复（可验证）
```

**审计视角**（等保/客户合规常问）：

| 问题 | 需要能回答 |
|---|---|
| 这个 CVE 修了吗？ | 是（热补丁 ID）还是"已随镜像 v2.3.1 修复" |
| 怎么证明修了？ | 补丁状态可查 / 镜像内源码或包版本可查 |
| 还有哪些实例没修？ | 实例 ↔ 补丁/镜像版本映射（台账要能出这个报表） |

## 8. CVE 应急决策树

```
CVE 通报
 ├─ 是否影响我的内核/组件？ ──否──► 记录并关闭
 ├─ 是否可被远程利用 / 已在野？ ──是──► 立即：热补丁（若能覆盖）+ 排期重建镜像
 │                                    （两条同时进行，不是二选一）
 └─ 否（本地/低危）
      ├─ 重建周期能否覆盖 SLA？ ──是──► 随下一次镜像发布修复（不入热补丁）
      └─ 否 ──► 热补丁止血 + 登记待收敛
```

**判据要点**：
- 先判断"**热补丁能否覆盖**"（改结构体的修复通常不能）→ 不能覆盖就只能重启/重建，必须提前排期
- 热补丁与重建**并行推进**，不要用"已打热补丁"作为推迟重建的理由

## 9. 四种更新方式的位置（与治理页呼应）

| 方式 | 生效速度 | 覆盖度 | 可复现 | 适用 |
|---|---|---|---|---|
| **重建镜像**（主干） | 慢 | 完整 | 高 | 常规发布、归档、合规基线 |
| **热补丁**（应急） | 快 | **部分** | 低 | 高危 CVE 的止血窗口 |
| 就地补丁 + 快照成新镜像 | 中 | 完整 | 中 | 救急但要产出可复用镜像时的折中 |
| bootc / 事务更新 | 中 | 完整 | 高 | 采用该范式的系统，支持原子回滚 |

## 10. 自测

1. 为什么热补丁只能"止血"？它改不了哪一类代码？
2. 打了热补丁之后，为什么"新扩容的实例仍然有洞"？这引出什么管理要求？
3. 热补丁与内核版本、编译配置是什么关系？为什么自编译内核难用？
4. 容器/K8s 节点场景下热补丁为什么收益更大？
5. 审计问"这个 CVE 修了吗"，你需要能拿出哪两样东西？
