# 云上 网络 细节 与 镜像 配置

> 前置：[[concepts/cloud-init 与 云元数据服务]]（network-config 的注入通道）、[[concepts/KVM 公有云 镜像 适配]] §7（网络适配主线）。
> 本页补齐主线里只有一句话带过的部分：IPv6、MTU、DNS、静态 IP、多网卡。

## 1. IPv6：云上"开了就完事"吗

多数云支持**双栈**（IPv4 + IPv6），但镜像侧有几处要确认：

| 项 | 说明 |
|---|---|
| 地址分配方式 | 通常 **SLAAC**（路由器通告）或 **DHCPv6**；IPv6 无 NAT，地址由平台下发 |
| **地址稳定性** | 内核默认可能用 **EUI-64**（含 MAC）或 **stable-privacy**（随机但稳定）生成接口标识 → 由 `addr_gen_mode` 控制；**换实例/换网卡后地址可能变**，任何"写死 IPv6 地址"的配置都会坏 |
| 内核参数 | `net.ifnames=0` 只影响网卡命名，不影响 IPv6；如要禁用需 `ipv6.disable=1`（慎用，很多工具依赖 IPv6 栈） |
| sysctl | `net.ipv6.conf.<if>.accept_ra`（是否接受 RA）、`autoconf`、`disable_ipv6` |
| cloud-init | network-config 的 v1/v2 都能表达 IPv6（v2 更清晰） |
| 防火墙/安全组 | 云安全组需单独放通 IPv6 规则（别以为 IPv4 通了就通） |

```bash
# 查看与验证
ip -6 addr show
ip -6 route show default
sysctl net.ipv6.conf.all.disable_ipv6 net.ipv6.conf.eth0.accept_ra
cat /proc/sys/net/ipv6/conf/eth0/addr_gen_mode
```

**结论**：IPv6 场景下**更不能用写死的地址**（比 IPv4 更容易因接口标识生成方式变化而失配），继续坚持 DHCP/RA 自动获取。

## 2. MTU 与巨帧：数据面场景的头号隐形杀手

| 场景 | 典型 MTU | 陷阱 |
|---|---|---|
| 普通云内网络 | **1500** | 最常见 |
| 支持巨帧的网络/实例族 | **8500 / 9000** | 需**端到端一致**，对端不支持就分片或丢包 |
| 叠加封装（VXLAN/Geneve/隧道） | **有效 MTU = 底层 MTU − 封装开销**（如 1500 − 50 = 1450） | 云端/私有云叠加网络下极易踩 |
| 数据面（DPDK/大包测试） | 取决于对端与中间设备 | 大包被静默丢弃 → 表现为"能 ping 小包、业务不通" |

**排查方法（PMTUD 黑洞的经典手法）**：

```bash
# 逐步加大 payload 并禁止分片，找出真实 MTU
ping -M do -s 1472 <目标IP>     # 1472 + 28 = 1500
ping -M do -s 1422 <目标IP>     # 1450 场景
# 网卡当前 MTU
ip link show eth0 | grep mtu
# 若已改过，写进配置（NM keyfile / ifcfg 的 MTU=）
```

**镜像侧要做的**：如果业务要求巨帧，**把 MTU 写进持久化网络配置**（而不是每次手工 `ip link set`），否则换实例/重启就回到 1500。

## 3. DNS / resolv.conf：谁在改它

`/etc/resolv.conf` 是个"多方争夺"的文件：

| 来源 | 行为 |
|---|---|
| NetworkManager | 由连接配置生成（`dns=` / `ipv4.dns`），常见做法是交给 NM 管 |
| DHCP | 下发 DNS 服务器地址 |
| cloud-init | 可写入（`manage_resolv_conf: true` 时） |
| 手工编辑 | **会被上面任一方覆盖** |

| 要点 | 建议 |
|---|---|
| 别手改 resolv.conf | 改 NM 连接配置或 `/etc/NetworkManager/conf.d/` |
| 云内 DNS 地址 | 用平台提供的内部 DNS（解析内网域名更快、更稳）；具体地址以厂商文档为准 |
| search domain | 内网服务用短名访问时依赖它；注入失败会导致"服务名解析不了" |
| 校验 | `resolvectl status`（NM）或 `nmcli dev show \| grep DNS` |

## 4. 静态 IP：公有云与私有云的不同口径

| 环境 | 通常做法 |
|---|---|
| **公有云** | **不改静态**：平台保证 DHCP 下发固定地址（你"看到的固定 IP"是平台层固定，不是 guest 静态配置） |
| **私有云 / 混合** | 常见**注入静态配置**（尤其客户环境无 DHCP）：cloud-init network-config v2 或平台侧注入 |

**风险点**：

- 在公有云里手工写静态 IP → 平台换网卡/换实例后冲突或不通
- 私有云里用 DHCP 但客户环境没有 DHCP 服务 → 起不来且看不到明显错误
- **结论**：明确目标环境是否有 DHCP，再决定用"DHCP"还是"注入静态"；镜像最好**两种都能适配**（cloud-init 覆盖式生成网络配置，而不是把某一种写死在镜像里）

## 5. 多网卡：默认路由冲突与策略路由

多网卡（内网+外网、管理+业务）在云上很常见：

| 问题 | 现象 | 处置 |
|---|---|---|
| 两个默认路由 | `ip route` 里出现两条 default，出流量走错网卡 | 只保留一条默认路由，其余用**策略路由**（`ip rule` + 独立路由表） |
| 源地址选择错 | 从 A 网卡进来的请求，回复从 B 网卡出去（对端拒绝） | `ip rule from <A网段> lookup <表A>`，或用 `rp_filter` 调优 |
| 辅助网卡未配置 | 云上 ENI 默认不透传配置（见主线 §7） | guest 内为辅助网卡单独配置（DHCP 或静态） |
| NM 自动接管顺序 | 多网卡时默认路由随连接激活顺序变化 | 在 NM 连接里显式设 `ipv4.never-default=yes`（辅助网卡） |

```bash
ip -4 route show; ip rule show
nmcli connection show --active
```

> 这条对 appliance 场景尤其重要：管理口与业务口分离时，**回复路径错**会导致"能进不能出"的诡异现象。

## 6. 检查清单

```
□ 目标环境是否有 DHCP（决定 DHCP 还是注入静态）
□ IPv6 是否启用：地址由 SLAAC/DHCPv6 获取，未写死地址
□ 需要巨帧时：MTU 已写进持久化网络配置，并与对端/中间设备一致
□ DNS：resolv.conf 归属明确（NM/cloud-init），未手工编辑
□ 多网卡：默认路由唯一；辅助网卡用策略路由或 never-default
□ 辅助网卡（ENI 类）已在 guest 内单独配置
□ 校验命令已纳入首次启动自检：ip addr / ip route / resolvectl / ping 大包
□ 网络异常时的排查顺序已明确：链路→地址→路由→DNS→MTU（见 §2）
```

**排障顺序速记**：`ip link`（网卡在不在）→ `ip addr`（地址有没有）→ `ip route`（路由对不对）→ `resolvectl`（DNS 通不通）→ `ping -M do -s`（MTU 有没有黑洞）。
