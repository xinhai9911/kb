# CI/CD 与测试策略

> 架构再好，没有可靠的交付与测试也会烂在发布环节。本文是工程效能骨架。

## 1. CI / CD / CD 三层

| 阶段 | 目标 | 关键 |
|------|------|------|
| **CI**（持续集成） | 每次提交自动构建+测试 | 快反馈（<10min）、主干开发 |
| **CD**（持续交付） | 随时可发布到生产 | 自动化部署流水线、一键发布 |
| **CD**（持续部署） | 通过流水线自动上生产 | 高置信测试 + 金丝雀 + 秒级回滚 |

> 核心原则：**小步快跑 + 自动化 + 可重复**。手动发布是不可靠之源。

## 2. 流水线阶段（典型）

```
代码提交
  → 构建 (编译/打包)
  → 静态检查 (lint/SAST)
  → 单元测试 (快)
  → 集成测试 (带依赖, 慢)
  → 制品入库 (镜像/包)
  → 部署到预发 (staging)
  → 冒烟测试
  → 灰度/金丝雀 → 全量
  → 监控告警 (见 [[concepts/可观测性工程]])
```

## 3. 测试金字塔

```
        /\       端到端 (E2E)   少、慢、贵、易碎
       /--\      集成测试        中
      /====\     单元测试        多、快、便宜、稳定
     /______\    
```
- **绝大多数测试应是单元测试**：快、定位准、无依赖。
- 集成测试覆盖「模块边界/外部依赖」。
- E2E 只保关键路径，太多会拖慢流水线且脆弱。
- 反模式：冰淇淋筒（全是 E2E，几乎没有单测）→ 反馈慢、维护痛。

## 4. 测试替身

| 替身 | 用途 |
|------|------|
| **Stub** | 返回固定值，隔离依赖 |
| **Mock** | 验证「是否按预期调用」（行为校验） |
| **Fake** | 轻量真实实现（内存 DB） |
| **Spy** | 部分真实+记录调用 |

> Mock 别滥用：过度 mock 让测试绑定实现细节，重构即碎。优先 fake/集成。

## 5. 契约测试（Consumer-Driven）

- 微服务跨团队协作时，消费者定义「我期望的 API 契约」，提供者 CI 校验满足。
- 工具：Pact。防止一方改接口悄悄破坏另一方。
- 比端到端测跨服务更稳、更快。

## 6. 发布策略

| 策略 | 机制 | 回滚 |
|------|------|------|
| 蓝绿 | 两套环境切流量 | 切回旧 |
| **金丝雀 (Canary)** | 先放 1–5% 流量观察 | 异常即停 |
| 滚动 | 逐批替换实例 | 中断剩余批次 |
| 影子 (Shadow) | 拷贝流量到新版本不接真用户 | 无影响 |

> 金丝雀必须配 [[concepts/可观测性工程\|SLO/错误预算]] 自动判定健康。回滚要秒级且演练过。

## 7. 特性开关（Feature Flag）

- 部署与发布解耦：代码上线但功能默认关，按用户/比例逐步开启。
- 支持「快速关掉坏功能」而无需重新发布。
- 注意：开关有生命周期，要定期清理，否则变技术债。

## 8. 常见反模式

| 反模式 | 后果 |
|--------|------|
| 主干长期分叉 | 合并地狱 |
| 测试只跑单测缺集成 | 边界 bug 漏网 |
| 手动发布 | 不一致、易错 |
| 无金丝雀直接全量 | 故障影响全部用户 |
| 回滚未演练 | 出事救不回 |
