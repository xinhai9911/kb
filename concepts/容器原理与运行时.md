# 容器原理与运行时（Container Internals & Runtime）

> 本文讲「容器本身」——它怎么来的、内核靠什么隔离它、镜像怎么分层、运行时栈如何把一条命令变成内核里的一个受限进程。
> 容器**之上**的分布式编排见 [[synthesis/Kubernetes 技术全景综述]]、[[concepts/Kubernetes 核心架构与组件]]；
> 容器**之间**的分布式难题（一致/共识/韧性）见 [[concepts/分布式系统基础]]、[[concepts/韧性设计]]。

## 0. 一句话定位

**容器 = 一个被加了「隔离视野 + 资源限额 + 独立文件系统视图」的普通 Linux 进程。**

它和你在终端里 `./app` 启动的进程没有本质区别——**共享同一个宿主机内核**，只是被内核的几项能力「关」在了一个受限的小世界里。这正是容器比虚拟机轻量的根本原因。

| 维度 | 虚拟机 (VM) | 容器 (Container) |
|---|---|---|
| 隔离层级 | 硬件级（Hypervisor 虚拟化 CPU/内存） | 进程级（内核 Namespace/Cgroups） |
| 内核 | 每个 VM 一个 Guest OS 内核 | **所有容器共享宿主机内核** |
| 启动 | 秒级~分钟级（要 boot） | 毫秒~百毫秒（只是起进程） |
| 体积 | GB 级 | MB 级（只打包应用+依赖） |
| 密度 | 低（几十个） | 高（上千个） |
| 安全边界 | 强（硬件隔离） | 较弱（共享内核，靠内核隔离 + 加固） |

> [!note] 强隔离需求
> 若需要比「共享内核」更强的边界（多租户/不可信代码），会用 **gVisor**（用户态内核拦截 syscalls）或 **Kata Containers**（每个容器跑在一个轻量 VM 里）。它们是「容器的体验、VM 的隔离」折中方案，不在本文基准范围内。

## 1. 容器的三大内核基石

一个容器之所以「看起来像一台独立的小机器」，全靠内核提供的三项能力组合：

| 基石 | 它解决什么 | 一句话 |
|---|---|---|
| **Namespace** | 隔离「能看到什么」 | 让进程以为自己独占 PID/网络/挂载… |
| **Cgroups** | 限制「能用多少」 | 给进程戴上 CPU/内存/IO 的「紧箍咒」 |
| **OverlayFS** | 隔离「文件系统视图」 | 分层叠加 + 写时复制，给每个容器一套独立根目录 |

三者相互独立又协同：Namespace 管「视野」，Cgroups 管「配额」，OverlayFS 管「磁盘」。缺少任何一个，容器都不完整。

---

## 2. 基石一：Namespace（隔离「看到什么」）

Namespace 把全局资源（PID、网络、挂载点…）做**按进程视图的虚拟化**。一个进程被放进某个 namespace 后，只能看到该 namespace 内的资源，以为自己独占了世界。

Linux 共有 7 类 Namespace：

| Namespace | 隔离内容 | 典型效果 |
|---|---|---|
| `mnt` (Mount) | 挂载点 | 每个容器有独立根文件系统 `/` |
| `pid` (PID) | 进程号 | 容器内 `ps` 只看到自己，PID 1 是自己的 init |
| `net` (Network) | 网络栈（IP/端口/路由/iptables） | 容器有独立 IP、网卡、端口空间 |
| `ipc` (IPC) | 进程间通信（共享内存/信号量） | 容器间 SysV IPC 不互通 |
| `uts` (UTS) | 主机名/域名 | 每个容器可设自己 hostname |
| `user` (User) | 用户/组映射 | 容器内 root 可映射到宿主普通用户（降权） |
| `time` (Time) | 系统时钟 | （较新）容器可拥有独立时间偏移 |

**动手感受**——用 `unshare` 临时创建一个隔离环境，体验「容器内核技术」的最小形态：

```bash
# 新建一个拥有独立 PID + 网络 + 挂载视图的 shell
sudo unshare --fork --pid --net --mount --mount-proc /bin/bash
# 现在在这个 shell 里：
echo $$        # 输出 1  —— 你成了 PID 1
ps aux         # 只看到自己，看不到宿主其它进程
hostname newc  # 改 hostname 不影响宿主
```

> 这正是 `runc` 在启动容器时做的核心动作之一：**`clone()` 带 `CLONE_NEWPID/CLONE_NEWNET/...` 标志创建新 namespace**，再把进程放进去。

## 3. 基石二：Cgroups（限制「能用多少」）

Namespace 让进程「看不见」别人，但如果不限制，一个容器仍能吃光整台机器的 CPU/内存把别人挤死。Cgroups（Control Groups）负责**配额与记账**。

| 子系统 | 控制什么 |
|---|---|
| `cpu` / `cpuacct` | CPU 时间片、配额、使用量统计 |
| `memory` | 内存上限（含 swap）、OOM 行为 |
| `pids` | 进程数上限（防 fork 炸弹） |
| `blkio` | 块设备 IO 带宽/吞吐 |
| `devices` | 能否访问某设备节点 |
| `freezer` | 暂停/恢复一组进程（K8s 调试用） |

**cgroups v1 vs v2**：
- **v1**：按子系统独立层级，灵活但复杂、易冲突。
- **v2**（主流）：统一单层级树，支持 **cgroup v2 原生资源控制**、`eBPF` 可编程调度钩子，K8s 1.25+ 默认推荐 v2。

**手动体验**（cgroups v2，路径在 `/sys/fs/cgroup`）：

```bash
# 建一个 cgroup，限制最多用 0.5 个 CPU、最多 100MB 内存
sudo mkdir /sys/fs/cgroup/demo
echo "50000 100000" | sudo tee /sys/fs/cgroup/demo/cpu.max   # 50% CPU
echo "100M"          | sudo tee /sys/fs/cgroup/demo/memory.max
# 把当前 shell 放进该 cgroup（之后它及其子进程都受限）
echo $$ | sudo tee /sys/fs/cgroup/demo/cgroup.procs
```

> [!warning] OOM 不是容器崩溃，是 cgroup 保护宿主
> 容器内存超 `memory.max` 时，内核在该 cgroup 内触发 **OOM Killer** 杀死容器内进程。这正是为什么「容器 OOM 被杀」通常表现为进程莫名退出（exit code 137 = SIGKILL）。

## 4. 基石三：OverlayFS（分层「怎么存」）

容器要有**自己独立的根文件系统**，但又不希望每个容器都复制一整份 OS（太浪费）。`OverlayFS` 用「分层叠加 + 写时复制（Copy-on-Write）」解决。

四个目录概念：

| 目录 | 角色 |
|---|---|
| `lowerdir` | 只读层（镜像各层，可多层叠加） |
| `upperdir` | 可写层（容器运行时产生的修改） |
| `workdir` | 内部临时工作目录（overlay 实现用） |
| `merged` | 合并后的统一视图（容器进程实际看到的 `/`） |

```
镜像层 (lower, 只读)       容器层 (upper, 可写)
  layer N  (app)    ┐
  layer 2  (deps)   ├─ 叠加 ─┐
  layer 1  (base)   ┘        ▼
                       merged (容器看到的完整根文件系统)
```

- **读**：文件在 upper 有就用 upper，否则从 lower 找。
- **改**：首次修改某文件，先从 lower **复制到 upper**（Copy-on-Write），再改 upper 副本——lower 永远不动。
- **删**：在 upper 放一个「whiteout」标记，遮住 lower 的同名文件。

> 好处：**镜像层全局共享**（10 个容器跑同一 nginx 镜像，磁盘只存一份层），**容器间互不污染**（各自有 upper）。

## 5. 容器镜像与 OCI 标准

「镜像」是容器的**静态模板**；「容器」是镜像的**运行实例**（就像「程序文件」vs「进程」）。

### 5.1 OCI 标准

为避免各家运行时互不兼容，社区定了 **OCI（Open Container Initiative）** 两个规范：

| 规范 | 规定什么 |
|---|---|
| **Image Spec** | 镜像格式：manifest + config + 若干 layer（tar 包），以及内容寻址（digest） |
| **Runtime Spec** | 怎么把一个解开的镜像「跑成」容器（config.json 描述进程、环境变量、namespace、mount…） |

> 任何遵循 OCI 的镜像（docker build 出的、或 podman/buildah 出的）都能被任何遵循 OCI 的运行时（runc/youki/crun）启动。这也是容器生态能互通的底层契约。

### 5.2 镜像的内部结构

```
myapp:latest
 ├─ manifest.json   —— 指向 config 与各 layer 的索引（含 digest）
 ├─ config.json     —— 镜像元数据：Entrypoint、环境变量、架构、层级顺序
 └─ layers/         —— 只读层 tar 包，按 Dockerfile 指令逐层叠加
      layer1.tar (FROM 基础镜像)
      layer2.tar (RUN apt install ...)
      layer3.tar (COPY app /app)
```

- **内容寻址**：每层用 `sha256:` digest 唯一标识。改一行代码 → 只有最上面那层 digest 变，下面层缓存复用。
- **分层缓存**：`docker build` 时命中缓存的层不重做，这就是为什么「把不常变的指令放前面」能大幅加速构建。

### 5.3 一条最小 Dockerfile

```dockerfile
FROM alpine:3.19              # layer1：基础系统（只读层，几乎所有镜像共享）
RUN apk add --no-cache python3 # layer2：装依赖
WORKDIR /app
COPY app.py .                  # layer3：应用代码
CMD ["python3", "app.py"]      # 容器启动命令
```

> [!tip] 镜像瘦身三板斧
> 1. 用 `alpine`/`distroless` 基础镜像；2. 多阶段构建（build 阶段编译，只把产物拷进运行镜像）；3. 合并 `RUN` 并清理缓存。镜像越小 → 拉取越快、攻击面越小。

## 6. 运行时栈：从 `docker run` 到内核

一条 `docker run` 背后是一条分层调用链。理解它，就理解了「命令 → 进程」的完整路径。

### 6.1 高层 vs 低层运行时

| 层级 | 组件 | 职责 |
|---|---|---|
| CLI | `docker` / `nerdctl` / `crictl` | 用户入口，发命令 |
| 高层运行时 (High-level) | `containerd` / `CRI-O` | 镜像管理、解包、调用低层、生命周期、**对外暴露 CRI 接口**（K8s 用） |
| 低层运行时 (Low-level) | `runc` / `crun` / `youki` | 严格按 OCI Runtime Spec，调用内核 `clone/setns/cgroupfs/pivot_root` 真正创建进程 |
| 内核 | Linux | Namespace / Cgroups / OverlayFS 实际执行隔离 |

### 6.2 调用链

```
docker CLI
   │ (REST/grpc)
   ▼
containerd          ← 镜像拉取/解包、快照(overlay)、事件、对外 CRI
   │ (grpc, 遵循 OCI)
   ▼
runc                ← 读 config.json，做内核系统调用
   │ clone(CLONE_NEW*) + setns + cgroupfs 写限额 + pivot_root 切换根 + exec
   ▼
容器进程（受限的普通进程，跑在独立 namespace/cgroup/overlay 里）
```

> K8s 视角：kubelet 不直接调 docker，而是通过 **CRI（Container Runtime Interface）** 调 `containerd` 或 `CRI-O`，再由它们调 `runc`。这就是 2020 年 K8s 移除 dockershim 后的标准链路（详见 [[concepts/Kubernetes 核心架构与组件]] 的数据面部分）。

### 6.3 `runc` 到底做了什么（伪流程）

```
1. 解析 OCI bundle（rootfs + config.json）
2. clone() 创建子进程，带 CLONE_NEWPID/NEWNET/NEWNS/...  → 新 namespace
3. 把子进程加入预先建好的 cgroup（CPU/内存限额生效）
4. 用 OverlayFS 挂载合并根文件系统到 rootfs
5. pivot_root 把合并目录切换为容器内的 "/"，脱离宿主根
6. 设置 uid/gid 映射（user namespace 降权）、环境变量
7. exec 目标程序（如 /app/server）—— 它成为容器内 PID 1
```

## 7. 从单容器到分布式：为什么需要编排

单容器解决了「**一个应用如何被干净、可复现地打包运行**」。但生产是**一群**容器跑在**一堆**机器上，单容器完全管不了这些：

| 分布式难题 | 单容器无能为力 | 编排层（K8s）的解法 |
|---|---|---|
| 调度到哪台机器 | 人肉挑 | Scheduler 按资源/亲和性自动选节点 |
| 挂了谁拉起 | 靠 systemd（单机） | ReplicaSet 控制循环跨节点自愈 |
| 多副本怎么暴露 | 手配负载均衡 | Service / Ingress 统一入口 |
| 配置/密钥 | 写死或挂盘 | ConfigMap / Secret |
| 升级/回滚 | 手动 | Deployment 滚动更新 |
| 跨节点网络互通 | 各容器各玩各的 | CNI  overlay 网络（见 [[entities/Cilium 容器网络]]） |
| 有状态/持久化 | 容器层随删随丢 | PV/PVC + StatefulSet（见 [[concepts/Kubernetes 存储体系]]） |

> **「容器分布式」= 把「容器」作为最小交付与调度单元，运行在一组通过网络互联、由共识协议协调的机器集群上。** 单容器是「零件」，分布式编排是「工厂」。

## 8. 容器在分布式场景下的核心挑战

容器进入分布式后，单机的隔离机制要面对**跨节点**的一致性与协作问题，这些恰恰是分布式系统的经典难题（可对照 [[concepts/分布式系统基础]]）：

1. **网络**：容器 IP 在节点间需互通且稳定（overlay 网络、CNI、Service 虚拟 IP、DNS 服务发现）。
2. **存储**：无状态易扩展；有状态需持久卷且「Pod 漂到哪卷跟到哪」，涉及 PV 调度与挂载（[[concepts/Kubernetes 存储体系]]）。
3. **协调/一致性**：集群「真相」靠 etcd + **Raft 共识**保证（谁主、配置写到哪要多数派确认）—— 见 [[concepts/分布式系统基础]] 共识算法一节。
4. **服务发现与配置**：配置热更新、密钥轮转，靠 ConfigMap/Secret + 控制循环下发。
5. **安全**：镜像供应链（签名/扫描）、Runtime 加固（降权、seccomp/AppArmor、只读根）、多租户隔离。
6. **可观测性**：容器生命周期短、数量多，需统一日志/指标/链路追踪（[[entities/可观测性接入实战]]、[[concepts/可观测性工程]]）。
7. **韧性**：限流、熔断、重试、超时在分布式调用链上仍是必答题（[[concepts/韧性设计]]、[[entities/限流熔断实战]]）。
