# 裸金属 与 私有云 的 镜像 差异

> 相关：[[concepts/KVM 公有云 镜像 适配]]（公有云主线）、[[concepts/Linux 启动链 与 引导]]（分区与固件基础）、
> [[concepts/云平台 镜像 与 云盘 产品语义]]（镜像生命周期）。
> 为什么单独成页：**公有云上验通 ≠ 能交付到客户现场**。客户常是 BMS 或 OpenStack 私有云。

## 1. 裸金属（BMS）：驱动需求变成"并集"

公有云 VM 里，guest 的盘都是虚拟设备 → 只需 virtio/NVMe 驱动。
BMS 是**物理机**，但云上又可能给它挂云盘 → 于是驱动需求是两者并集：

| 盘的类型 | 需要的驱动 | 说明 |
|---|---|---|
| 本地物理盘（RAID/HBA 后） | `megaraid_sas` / `mpt3sas` / `hpsa` / `smartpqi` 等 **厂商驱动** | 这才是 BMS 与 VM 的最大差别 |
| 云盘（挂到 BMS） | `virtio_blk` / `nvme` | 部分 BMS 挂云盘仍走 virtio 或 NVMe |
| 本地 NVMe SSD | `nvme` | — |
| 网卡 | 真实网卡驱动（ixgbe/i40e/mlx5…）或 virtio_net | 视机型 |

**结论**：BMS 镜像的 initramfs 驱动清单要**在云 VM 清单之外，加上真实存储控制器驱动**；
`hostonly=yes` 生成的 initramfs 在 BMS 上尤其容易挂（这正是 [[concepts/initramfs 与 dracut]] §3.3 的坑）。

### 1.1 一个反直觉口径：UEFI 镜像仍可能是 MBR

**华为云 BMS 文档口径**：x86 裸金属用 UEFI 启动时，**仍然要求采用 MBR 分区表**，并必须有 `boot_efi` 分区
（UEFI 规范本身允许 MBR——GPT 是常见做法而非强制）。

> 这与公有云 VM 侧"UEFI 必须 GPT"的直觉相反。教训：**分区表格式与引导方式的关系要看具体平台文档**，
> 不要用一条规则套所有场景（[[concepts/Linux 启动链 与 引导]] §2.1 给的是常规关系，不是定理）。

### 1.2 启动链路：带外管理与 iPXE（与 VM 最大的流程差异）

VM 的启动是"固件直接读系统盘"；**BMS 的启动链路多了一段平台侧流程**：

```
带外管理（BMC / IPMI / Redfish 类接口，用户通常拿不到）
   └─ 平台把镜像/部署包通过 网络引导（PXE/iPXE） 拉起
       └─ 写入本地盘（可能在 RAID 卡后）
           └─ 设置 boot order → 从本地盘引导
```

**对交付的三个实际影响**：

| 影响 | 说明 |
|---|---|
| 镜像的"角色"不同 | 平台要的是**可写入本地盘的磁盘镜像（qcow2/raw 等）**，不是 ISO 安装器；用安装 ISO 当"镜像"提交会卡在第一步 |
| 引导顺序由平台/固件决定 | BMS 有自己的固件设置（可能集中在平台侧）；起不来时**先确认是否走完了平台部署流程**，而不是只看 OS 日志 |
| RAID 卡会改变"盘的样子" | 本地盘常在 RAID 卡后 → 虚拟盘容量/扇区/命名与物理盘不同；镜像里的分区与扩容假设要重新核对（这也是 §1 驱动并集的另一面） |

**排查顺序建议（BMS 起不来时）**：

1. 平台侧状态：镜像转换/部署任务是否成功（不是"已导入"就等于"已部署"）
2. 网络引导阶段：是否进入 PXE/iPXE、是否拿到部署包
3. 本地盘：RAID 逻辑盘是否创建、容量是否符合预期
4. OS 阶段：initramfs 是否含 RAID/HBA 驱动（§1 清单）
5. 最后才是常规的启动链排障（[[concepts/Linux 启动链 与 引导]] §6）

> 注：各家 BMS 的带外与网络引导实现细节不同（是否暴露给用户、是否支持自定义 iPXE 脚本），
> **以目标平台文档为准**；本节的判断只依赖"链路比 VM 长一段平台流程"这一结构性事实。

### 1.3 整机镜像 vs 系统盘镜像

| 类型 | 内容 | 适用 |
|---|---|---|
| 系统盘镜像 | 仅系统盘 → 创建实例只需再挂数据盘 | 标准做法 |
| **整机镜像** | 系统盘 + 数据盘（一次带走全部） | 一体化 appliance / 需要预置数据盘数据的场景 |

> appliance 类交付常需要**整机镜像**，因为业务数据或初始化数据在数据盘上。

### 1.4 迁移到 BMS 的路径

- 云厂商迁移工具（阿里云 SMC 等）支持物理机/其他云**迁移到 BMS**（见 [[concepts/KVM 公有云 镜像 适配]] §14）
- 迁移工具会自动处理驱动注入，但**分区/引导结构不会替你按 BMS 规范重排** → 迁移后仍要验收
- 自制镜像走"导入 → 用 BMS 规格创建实例"路径时，务必确认目标机型支持该镜像的启动模式

### 1.5 BMS 检查清单

```
□ 交付物形态正确：可写入本地盘的磁盘镜像（不是 ISO 安装器）
□ initramfs 含真实存储控制器驱动（megaraid_sas/mpt3sas/hpsa…）+ virtio/nvme（挂云盘时）
□ 未开启 hostonly（或已显式 add_drivers 兜底）
□ 分区表格式与启动模式符合该平台文档（注意 MBR+UEFI 这类反直觉口径）
□ RAID 逻辑盘的容量/扇区假设已核对（扩容链路重新验算）
□ 是否交付整机镜像（含数据盘）
□ 平台侧部署流程可用（网络引导/带外手段）与救援路径
□ 目标 BMS 机型是否支持该启动模式与镜像架构
```

## 2. 私有云（OpenStack）：镜像要靠"属性"声明

公有云是"上传 + 导入时选参数"；OpenStack 是"**上传 + 在镜像上写属性**"。
属性写错/漏写，实例可能起不来或行为异常。

### 2.1 Glance 常用镜像属性（官方清单）

| 属性 | 取值 | 作用 / 配错后果 |
|---|---|---|
| `hw_disk_bus` | `virtio` / `scsi` / `ide` / `usb`（KVM/QEMU 下；还含 `uml`/`xen`/`lxc`） | 磁盘挂到哪种控制器。配 `ide` → 设备名与性能都变；漏配则用驱动默认 |
| `hw_scsi_model` | `virtio-scsi` | 启用 virtio-scsi 替代默认 virtio-blk |
| `hw_firmware_type` | `bios` / `uefi` | **引导固件类型**，与镜像实际不符 → 起不来（对应公有云"启动模式声明"） |
| `hw_machine_type` | libvirt：`virsh capabilities` 里的机型；Hyper-V：`hyperv-gen1/2` | **ARM 镜像**未指定时 libvirt 默认 `virt`；Hyper-V 第 2 代必须显式声明 |
| `hw_vif_model` | KVM：`virtio` / `e1000` / `e1000e` / `rtl8139` / `vmxnet3` / `igb` … | 网卡模型；配错 → 无网卡或性能差 |
| `hw_qemu_guest_agent` | `yes` / `no` | 是否启用 qemu-guest-agent（优雅关机/冻结文件系统） |
| `img_config_drive` | `mandatory` / `optional`（默认） | 是否必须有 config drive（元数据注入的载体） |
| `hypervisor_type` | `qemu`（KVM 也用 qemu）/ `xen` / `vmware` / `ironic` … | 混合虚拟化环境中把镜像匹配到正确 hypervisor |
| `os_type` | `linux` / `windows` | 影响 libvirt 行为（如 windows 会建 FAT32 swap 分区、限制主机名长度、启用 Hyper-V  enlightenments） |
| `hw_video_model` | 如 `none` | `none` 禁用图形设备（GPU 直通场景） |
| `hw_boot_menu` | `true` / `false` | 启用启动菜单（排障有用） |
| `hw_mem_encryption` / `_model` | bool / `amd-sev` 等 | 内存加密（需硬件支持） |

```bash
# 上传并声明属性（示例）
openstack image create "appliance-2026.10" \
  --disk-format qcow2 --container-format bare \
  --file appliance.qcow2 \
  --property hw_disk_bus=virtio \
  --property hw_scsi_model=virtio-scsi \
  --property hw_firmware_type=uefi \
  --property hw_qemu_guest_agent=yes \
  --property os_type=linux

# 改属性
openstack image set --property hw_firmware_type=bios <image>
```

### 2.2 两个容易踩的边界

1. **Glance 没有 NVMe 相关属性**（官方属性清单中不存在 NVMe 属性）
   → OpenStack 侧"用不用 NVMe"取决于 Nova/hypervisor 配置与 guest 内驱动，不是镜像属性
   → 对镜像的要求回到原点：**initramfs 里必须有 `nvme`**（与公有云一致）
2. `os_require_quiesce` 之类并不在 Glance 属性清单中（属 Nova/Cinder 侧的快照静默语义）
   → 别把"听说过的属性"直接往上写，以目标版本的官方清单为准

### 2.3 元数据与 config drive

| 机制 | 说明 |
|---|---|
| metadata 服务 | 实例内访问 `169.254.169.254` 取 instance-id/hostname/keypair |
| **config drive** | 挂一个只读卷（label `config-2`），内含元数据与 user-data；**网络未就绪时也能初始化** |
| datasource | cloud-init 需能识别 `OpenStack`（通常内置；自裁发行版要确认） |

> 与公有云的差别：阿里云用专用地址 `100.100.100.200`；OpenStack 用 169.254.169.254 + config drive。
> cloud-init 的 datasource 列表里若没有 `OpenStack`，会表现为"探测超时后跳过初始化"（见 [[concepts/cloud-init 与 云元数据服务]] §6）。

## 3. 公有云 vs 私有云 对照表

| 维度 | 公有云（阿里/腾讯/华为） | 私有云（OpenStack） |
|---|---|---|
| 上传通道 | OSS/OBS/COS → 导入镜像 | Glance API 直接上传 |
| 磁盘总线 | 平台按规格决定（virtio-blk/scsi/NVMe） | **镜像属性 `hw_disk_bus`/`hw_scsi_model` 声明** |
| 启动固件 | 导入时声明启动模式 + 规格限制 | `hw_firmware_type` 属性 |
| CPU 架构匹配 | 导入时选架构，规格族限定 | `hw_machine_type`（ARM 默认 `virt`）+ 计算节点能力 |
| 网络模型 | DHCP + 厂商 ENI/辅助网卡 | Neutron：可能静态注入、`hw_vif_model` |
| 元数据 | 厂商专有地址 + 专有 datasource | 169.254.169.254 + ConfigDrive（datasource=OpenStack） |
| 厂商 agent | 云助手（必装）/ CloudResetPwdAgent | qemu-guest-agent（可选，靠属性开启） |
| 系统盘扩容 | 平台自动 + cloud-init growpart | growpart（可能靠 DIB 的 growroot element） |
| 镜像格式 | qcow2/raw/vhd/vmdk | qcow2 为主（Glance 支持多种） |
| 失败模式 | 参数填错 / 驱动缺失 | **属性漏配** / 驱动缺失 / datasource 未识别 |

## 4. 交付到客户私有云的检查清单

```
□ 驱动全集：virtio_blk / virtio_scsi / nvme / xfs（+ BMS 场景的真实 RAID/HBA 驱动）
□ 未依赖公有云专有 agent（云助手、CloudResetPwdAgent）——私有云没有这些
□ cloud-init 的 datasource 列表包含 OpenStack / ConfigDrive / NoCloud
□ 不写死设备名（vda/sda/nvme0n1 三种都可能出现）→ fstab 与 grub 全 UUID
□ 分区表与引导方式符合目标平台文档（注意 BMS 的 MBR+UEFI 口径）
□ 目标侧需要声明的属性清单已备好（hw_disk_bus / hw_firmware_type / img_config_drive …）
□ 三种总线（virtio / scsi / ide）至少各验证一次（私有云 operator 可能配不同）
□ 元数据可达性验证（169.254.169.254）与首次启动 cloud-init 结果
□ 版本可追溯：镜像 sha256 + 构建号 + 组件清单随交付物一起给（见 [[concepts/镜像 资产 治理 与 成本]]）
```
