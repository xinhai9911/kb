# 关系型数据库内核（MySQL/PostgreSQL）

> 库里已有 NoSQL（HBase/ES/InfluxDB，见 [[20-protocols/elasticsearch]] 等），但缺关系型内核。本文补这块。
> 事务与一致性原理衔接 [[concepts/分布式系统基础]]。

---

## 1. 存储：B+ 树与聚簇索引

InnoDB 用 **B+ 树**组织数据：

- **聚簇索引（Clustered）**：主键即数据本身，叶子节点存整行；按主键查极快。
- **二级索引**：叶子存「主键值」，回表（含一次聚簇索引查找）拿整行。
- **缓冲池（Buffer Pool）**：缓存数据页，命中走内存；LRU 管理。这是性能核心（类比 [[concepts/Redis 缓存与数据结构]] 但内置）。
- 为什么 B+ 树：矮胖（3~4 层覆盖亿级行）、叶子链表支持范围扫描。

> [!note] 索引最左前缀
> 联合索引 `(a,b,c)` 只从左匹配：`WHERE a=1 AND b=2` 用得上，`WHERE b=2` 用不上——设计索引按查询顺序。

## 2. 事务与隔离级别

**ACID**：原子性（undo log 回滚）、一致性（约束）、隔离性（下面）、持久性（redo log/WAL）。

| 隔离级别 | 现象 | 实现 |
|---|---|---|
| Read Uncommitted | 脏读 | 几乎不用 |
| Read Committed (RC) | 不可重复读 | 语句级快照 |
| **Repeatable Read (RR，MySQL 默认)** | 幻读（InnoDB 靠 MVCC+间隙锁基本避免） | 事务级快照 |
| Serializable | 全串行 | 锁/范围锁 |

**MVCC（多版本并发控制）**：每行藏隐藏事务 ID，读不加锁，读「快照版本」——读写不阻塞。靠 **undo log** 存历史版本实现回滚与旧快照。

### InnoDB 锁类型

| 锁类型 | 粒度 | 行为 |
|---|---|---|
| **Record Lock** | 单行 | 锁住索引记录本身 |
| **Gap Lock** | 间隙 | 锁住索引记录之间的间隙（防幻读插入） |
| **Next-Key Lock** | 行+间隙 | Record + Gap 组合（RR 级别默认，左开右闭） |
| **意向锁** | 表级 | IS/IX：标识事务要加行锁，加速表锁判断 |

> [!note] RR 级别防幻读
> InnoDB 在 RR 下用 Next-Key Lock 锁住范围，新插入的行会被间隙锁阻塞，从而避免幻读。

### PostgreSQL MVCC 差异

MySQL 用 **undo log** 存旧版本（在 undo 表空间）；PostgreSQL 把旧版本**直接存在数据页中**（tuple header 标记 xmin/xmax）。
- **MySQL**：旧版本在单独位置，数据页保持最新，compact。
- **PostgreSQL**：旧版本在原位，需要 `VACUUM` 清理死元组（类似 GC，[[concepts/Go 运行时与并发模型]] 三色标记的思路）。
- PostgreSQL 的 `VACUUM` 是运维关键：不清理会导致表膨胀。

## 3. 写入与崩溃恢复（WAL）

- **WAL（Write-Ahead Logging）**：改数据前先写 redo log（顺序写，快），再异步刷数据页。崩溃后靠 redo 重放恢复——保证持久性。
- **redo log**：物理日志，重放崩溃前未落盘修改。
- **binlog**：逻辑日志（server 层），用于主从复制/位点恢复。
- **两阶段提交**：redo 与 binlog 一致（prepare → commit），保证主从不裂。

> 顺序写日志换随机写数据页的性能——同 [[concepts/Kafka 消息队列与流处理]] 的「追加写日志」思路，也呼应 [[concepts/存储栈与io_uring]] 的 IO 优化。

## 4. 查询执行

- 优化器选执行计划：全表扫描 vs 索引、join 顺序。
- `EXPLAIN` 看 `type`（const/ref/range/index/all）、`rows`、`key`。
- 慢查询：缺索引、隐式类型转换使索引失效、深分页（`LIMIT 1000000` 慢）。

### 索引设计最佳实践

| 策略 | 说明 |
|---|---|
| **覆盖索引** | 索引包含查询所有列，无需回表（`EXPLAIN` 显示 `Using index`） |
| **前缀索引** | 长字符串只索引前 N 字符，省空间（`INDEX (name(10))`） |
| **函数索引** | 对表达式建索引：`INDEX ((UPPER(email)))`，让 `WHERE UPPER(email)=...` 走索引 |
| **最左前缀** | 联合索引 `(a,b,c)`：`a` / `a,b` / `a,b,c` 可用；`b,c` 不可用 |
| **避免过多索引** | 每个索引增加写入开销（B+ 树维护），OLTP 场景 5-6 个为宜 |

> [!warning] 深分页优化
> `LIMIT 1000000, 10` 需扫描前 100 万行再丢弃。改用游标分页：`WHERE id > last_id ORDER BY id LIMIT 10`（利用主键索引）。

### 查询优化器（CBO）

现代 DB 用 **Cost-Based Optimizer（CBO）**：基于统计信息（行数/NDV/直方图）估算每种执行计划的 IO/CPU 代价，选最低的。
- **统计信息过期**：`ANALYZE TABLE` 更新（PostgreSQL: `ANALYZE`），否则优化器选错计划。
- **Hint**：MySQL 用 `/*+ INDEX(...) */` 强制走索引（最后手段）。

## 5. 与 NoSQL 定位对比

| 维度 | 关系型（MySQL/PG） | NoSQL（HBase/ES） |
|---|---|---|
| 模型 | 表/行/强 Schema | 列族/文档/宽表 |
| 事务 | 完整 ACID | 弱/单行 |
| 查询 | 复杂 SQL join | 简单 KV/检索 |
| 扩展 | 垂直为主（或分库分表） | 天然水平 |

> 选型：强一致+复杂查询用关系型；海量+高吞吐+弱一致用 NoSQL。二者常配合（[[concepts/Redis 缓存与数据结构]] 挡前面，关系型落底）。
