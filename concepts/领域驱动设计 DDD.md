# 领域驱动设计 DDD

> DDD 不是技术框架，而是**用代码建模业务**的方法论。微服务拆分常以限界上下文为边界（[[entities/微服务拆分实战]]）。

## 1. 核心思想

- 把**业务复杂度**放在首位，技术只是支撑。
- 开发与技术专家共用一套**通用语言（Ubiquitous Language）**：代码里的类名/方法名 = 业务对话里的词。歧义词消除 → 模型准确。
- 反例：代码全是 `Manager`/`Handler`/`DTO`，看不出业务。

## 2. 限界上下文（Bounded Context）

- 把大系统按**语义边界**切分成多个上下文，每个上下文内模型自洽。
- 同一个词在不同上下文含义不同：`Account` 在「账单上下文」是账单，在「认证上下文」是账号——必须分开建模。
- 微服务边界 ≈ 限界上下文边界（强相关但非绝对）。

## 3. 上下文映射（Integration）

| 模式 | 说明 |
|------|------|
| **防腐层 (ACL)** | 下游在己方上下文包一层适配，挡住上游模型侵入 |
| 共享内核 | 两上下文共用一小块模型（谨慎，易耦合） |
| 开放主机服务 (OHS) | 上游暴露稳定协议/API（如 [[concepts/API 设计]]） |
| 遵奉者/分离方式 | 跟从或彻底独立 |

> ACL 极实用：接老系统/第三方时别让它的烂模型污染你的核心域。

## 4. 实体 / 值对象 / 聚合

| 概念 | 特征 |
|------|------|
| **实体 (Entity)** | 有唯一标识、有生命周期（`Order` 用 id 区分，状态变仍是同一单） |
| **值对象 (Value Object)** | 无标识、靠属性值相等（`Money`、`Address`；不可变） |
| **聚合 (Aggregate)** | 一组相关对象的边界，外部只通过**聚合根**访问，保证内部一致性 |

- **聚合根 (Aggregate Root)**：聚合的入口实体；跨聚合修改不允许直接引用内部，要走根。
- 聚合设计原则：**一个事务只改一个聚合**（否则分布式事务，见 [[concepts/分布式系统基础]] §4）。

## 5. 领域事件（Domain Event）

- 领域内发生的重要事实：`OrderPlaced`、`PaymentReceived`。
- 解耦：本聚合发事件，其他上下文（或 [[concepts/架构风格演进\|事件驱动]] 总线）消费响应。
- 天然衔接事件驱动架构与 CQRS 投影。

## 6. 仓储（Repository）

- 聚合的持久化抽象：「存/取聚合」像集合，屏蔽 DB 细节。
- 注意：Repository 按**聚合根**而非每个表建；对应 [[concepts/软件设计原则与代码质量\|依赖倒置]]。

## 7. 战术 vs 战略

- **战略 DDD**（限界上下文、通用语言、映射）：决定**怎么切**，价值最大，直接指导微服务。
- **战术 DDD**（实体/值对象/聚合/工厂/仓储）：决定**怎么写**，落在代码层。

## 8. 与微服务的关系

```
限界上下文 ──映射──► 微服务边界
通用语言 ──────► 服务内模型命名
聚合根 ───────► 事务/一致性边界
领域事件 ─────► 服务间异步通信
```
> 但 DDD 不要求微服务：模块化单体里也能用限界上下文 + 聚合（[[concepts/架构风格演进]] §2）。
