# 关键词检索（BM25）+ 语义检索双路，融合排序

## 一句话定义

**混合检索 (Hybrid Retrieval)**:同一查询同时经过一条"关键词通道"(BM25 / 倒排索引)和一条"语义通道"(向量相似度 / ANN),再把两路 Top-K 结果在**融合层 (Fusion)** 合并排序,作为下游 RAG / 问答 / 推荐的召回来源。

## 它在解决什么问题

单路检索都有不可消除的盲区:

| 检索方式 | 强项 | 弱项 |
|---|---|---|
| **BM25 (词面匹配)** | 精确术语、代码、专有名词、缩写、错别字容忍(配合 fuzzy) | 同义改写("电动车" vs "新能源汽车")、跨语言、概念泛化 |
| **向量检索 (语义)** | 语义相似、改写、跨语言、长尾概念 | 错过精确术语、对罕见专有名词召回差、对**关键词干扰**(无关但相似)敏感 |

**融合排序的核心价值**:两路互补,既不漏掉"用户原话里的关键术语",也不漏掉"用户想说但没写出来的语义"。这是工业级搜索/RAG 的事实标准,Elasticsearch(BM25 + ELSER dense_vector)、OpenSearch(Neural Search)、Weaviate hybrid、Milvus hybrid search、Pinecone sparse-dense index、Qdrant fusion 全部默认走这条路。

## 架构总览

```
                         ┌─→ BM25 倒排索引 ─→ Top-K_bm25 (score_bm25)
                         │       │
   Query ─── 预处理 ───┬──┤       │
                      │  │       ↓
                      │  │   融合层 (Fusion)
                      │  │       ↑
                      │  └─→ 向量检索 (ANN, dense + optional sparse) ─→ Top-K_dense
                      │              ↑
                      └─→ Embedding 模型 ─────────────┘
                              ↓
                       重排 (Reranker) → Top-N 给 LLM
```

关键组件:

1. **预处理**:分词、归一化、可能的多语种切分;embedding 端用同一模型离线编码所有文档。
2. **BM25 通道**:基于倒排索引,计算 query 与 doc 的 BM25 分数(对词频 TF、文档频率 IDF、长度归一化建模)。
3. **向量通道**:离线用 sentence-transformer / BGE / OpenAI text-embedding-3 等模型把文档向量化,在线只编码 query,做近似最近邻 (ANN) 检索(IVF / HNSW / ScaNN)。
4. **融合层**:把两路分数合并(见下)。
5. **可选重排**:在融合后,再用一个 cross-encoder reranker(例如 bge-reranker、Cohere Rerank)对前 N 条精排。Rerank 提升明显但有 latency 成本,通常 N=20~50。

## BM25 通道

### 公式与直觉

$$
\text{BM25}(q, d) = \sum_{t \in q} \text{IDF}(t) \cdot \frac{f(t, d) \cdot (k_1 + 1)}{f(t, d) + k_1 \cdot \left(1 - b + b \cdot \frac{|d|}{\text{avgdl}}\right)}
$$

- `f(t,d)` = 词 t 在文档 d 中出现次数
- `|d| / avgdl` = 文档长度归一化(长文档天然词多,需要折损)
- `k1` 控制词频饱和速度(常用 1.2~2.0),`b` 控制长度归一化强度(常用 0.75)
- `IDF(t) = log((N - df + 0.5) / (df + 0.5) + 1)`,罕见词权重高

### 工程要点
- 需要分词器;中文常用 jieba / HanLP / IK Analyzer
- 同义词扩展可补强(但要小心召回噪声)
- 适合"短查询 + 短文档"和"用户原话带专有名词"的场景

## 向量检索通道

### 离线编码
- 文档切 chunk(经验值 200~512 tokens,重叠 10%~20%)
- 选 embedding 模型:BGE-M3 / E5 / m3e / OpenAI text-embedding-3-large / Cohere embed-v3
- 多语言场景必须用多语言模型

### 在线检索
- ANN 索引:HNSW(高召回、高内存)、IVF-PQ(压缩、省内存)、ScaNN
- 距离:cosine similarity / dot product / L2,模型训练时用哪种就保持一致
- 元数据过滤:时间、权限、来源(常用 hybrid index: dense vector + sparse BM25 + filterable metadata)

## 融合层:RRF vs 加权打分

### 方法 A — 倒数排名融合 (RRF, 业界默认)

$$
\text{score}_{\text{RRF}}(d) = \sum_{r \in \{\text{bm25, dense}\}} \frac{1}{k + \text{rank}_r(d)}
$$

- `k` 是平滑常数(常用 60)
- **只看排名,不看原始分数** → 完全屏蔽两路分数量纲差异,实现最简单
- 两路都给同一个 doc 时,分数相加 → 自然提升共识结果

### 方法 B — 线性加权

$$
\text{score} = \alpha \cdot \text{norm}(\text{score}_{\text{bm25}}) + (1 - \alpha) \cdot \text{norm}(\text{score}_{\text{dense}})
$$

- 需要先各自归一化(min-max / z-score / rank-percentile)
- `α` 需调参,BM25 主导的查询 vs 语义主导的查询最优 `α` 不同
- 缺点:静态权重难适配不同 query

### 方法 C — 学习排序 (LTR)
- 把两路分数 + 查询特征 + 文档特征喂给 LambdaMART / XGBoost
- 需标注数据(相关性 0/1/2),冷启动不友好
- 追求极致排序质量时考虑

**实战首选 RRF**:零调参、对量纲鲁棒、效果与 LTR 接近(经验差距 <5% NDCG@10)。

## 可选:重排 (Rerank)

融合后取前 50~100 条,送 cross-encoder reranker(bert-style 模型同时看到 query 和 doc)做精排:
- 输入:`[CLS] query [SEP] doc`
- 输出:相关性分数
- **效果**:NDCG@10 通常再涨 5%~15%
- **代价**:每条 ~10ms CPU,100 条 = 1s,需要控量或异步
- 服务:Cohere Rerank API、bge-reranker-v2、Jina Rerank

## 何时必须用双路

- 领域有大量**专有名词、缩写、代码、版本号**(BM25 强)
- 用户查询存在**口语化 / 改写 / 拼写变体**(语义强)
- 召回率是首要 KPI(FAQ / 客服 / 法律 / 医疗 / 知识库)
- 多语种混排

## 何时可只走单路

- 数据集高度结构化、术语固定(如 SQL schema 检索)— BM25 足够
- 完全开放域聊天,所有内容都已经向量化且无强术语 — dense 足够
- 极端 latency 约束(<10ms)— 单路 IVF

## 工程化 Checklist

- [ ] **分块策略**:chunk 大小、重叠、是否保留小标题/表格结构
- [ ] **Embedding 选型**:中文/多语言?维度?最大 token?MTEB 榜单参考但不迷信
- [ ] **元数据过滤**:时间、权限、来源必须在向量索引外另存一份
- [ ] **冷启动**:新文档多久可被检索到(同步写 vs 异步批量)?
- [ ] **评测集**:至少 50 条真实 query + 人工相关性标注,跑 NDCG@10 / Recall@K / MRR
- [ ] **A/B 框架**:能切单路 vs 双路 vs 双路+rerank 三档对比
- [ ] **可观测**:召回来源分布(bm25-only / dense-only / both),用来发现哪路退化
- [ ] **降级**:向量通道挂了,BM25 必须能独立服务

## 评估指标

- **Recall@K**:Top-K 里包含相关文档的比例(召回)
- **NDCG@K**:考虑排序位置的相关性加权(主流综合指标)
- **MRR**:第一个相关结果的倒数排名(单答案场景)
- **Hit Rate@K**:Top-K 中是否有任一相关(最宽松)
- 业务侧再加:**端到端 RAG 答案正确率 / 引用准确率**

## 常见反模式

1. **盲目相信 embedding 相似度** — 相似 ≠ 相关。RAG 里 dense 召回堆在前面的常常是"主题相近但答不了问题"的文档,这就是为什么必须配 BM25 + rerank。
2. **chunk 切太大** — 512 token 一片、整段塞进 prompt,语义噪声爆表。混合检索救不了烂 chunk。
3. **embedding 模型不匹配语种** — 用英文模型搜中文 = 灾难。
4. **没有过滤 = 数据泄露** — 用户的权限/时间窗要在向量库外另存,不能只靠相似度。
5. **两路 Top-K 设一样大** — 通常 dense 给 100、BM25 给 50,RRF 前 K 取 30~50 即可,rerank 再精。

## 与知识库 (QMD / Obsidian vault) 的关系

本知识库正在搭建本地向量化检索(qmd 嵌 embedding)。"双路融合"是这条路的**默认终态**:

- 关键词路:Obsidian 自带搜索 + ripgrep,做精确标题/标签命中
- 语义路:qmd 跑 BGE / m3e embedding,做"我想到意思但记不清措辞"的查询
- 融合:RRF,top-30 → 可选 cross-encoder rerank
- 评估:用 `/wiki-query 摄影` 这种已验证 query 做回归测试
