# 设计模式精讲

> 原则（[[concepts/软件设计原则与代码质量]]）是「为什么」，模式是「怎么做」的可复用方案。本文按 GoF 三类梳理最常用的模式与误用。

## 1. 创建型（对象怎么来）

| 模式 | 解决 | 现代替代 |
|------|------|---------|
| **工厂方法 / 抽象工厂** | 屏蔽对象创建细节、按配置造不同实现 | DI 容器（Spring/Guice）、构造函数注入 |
| **单例** | 全局唯一实例 | 多被滥用；优先「依赖注入 + 作用域」而非全局可变状态 |
| **建造者** | 多参数/分步构造复杂对象 | 具名参数/流式 builder（如 OkHttp、StringBuilder） |
| **原型** | 高效克隆 | 少用，现代多用值对象 + 拷贝 |

> 单例是**最常被误用**的模式：它引入全局隐藏依赖、阻碍测试、破坏并发安全。能用注入就别用单例。

## 2. 结构型（对象怎么组合）

| 模式 | 解决 | 例子 |
|------|------|------|
| **适配器** | 接口不兼容两边对接 | 旧 SDK 包一层新接口 |
| **装饰器** | 不改动原类动态加职责 | Java I/O、`http.Handler` 包装、[[concepts/Nginx 框架内部实现\|Nginx filter 链]] |
| **代理** | 控制/增强访问（懒加载、鉴权、缓存） | 远程代理、虚拟代理、AOP |
| **桥接** | 抽象与实现解耦各自演进 | 多平台 UI + 多渲染后端 |
| **组合** | 树形结构统一处理叶子与容器 | 文件系统、AST |
| **外观** | 给复杂子系统提供简单入口 | SDK 门面、API Gateway |
| **享元** | 共享细粒度对象降内存 | 字符串池、连接池 |

> [!note] Nginx filter 链即装饰器模式
> **Nginx 的 filter 链本身就是装饰器模式的典型实现**（见 [[concepts/Nginx 框架内部实现]] §6）：每个 filter 包裹响应，链式叠加。

## 3. 行为型（对象怎么协作）

| 模式 | 解决 | 例子 |
|------|------|------|
| **策略** | 运行时切换算法 | 压缩算法、负载均衡（见 [[entities/Nginx 模块开发实战\|Nginx 负载均衡器模块]]） |
| **观察者 / 发布订阅** | 状态变化通知多方 | 事件总线、[[concepts/架构风格演进\|事件驱动架构]] |
| **责任链** | 请求过多个处理器 | 中间件、HTTP 拦截器、Nginx phase 链 |
| **命令** | 把请求封装成对象（可排队/撤销） | 事务队列、CQRS 命令 |
| **模板方法** | 固定骨架、留钩子给子类 | 框架生命周期回调 |
| **状态** | 对象行为随状态变 | 连接状态机、订单状态 |
| **迭代器 / 访问者** | 遍历/分派 | 集合遍历、编译器 AST 遍历 |

> **责任链** 与 **策略** 在框架里极常见：Nginx 的 11 阶段 handler（[[concepts/Nginx 架构与事件模型]] §3）是责任链；可插拔负载均衡算法是策略。

## 4. 反模式（比缺模式更危险）

| 反模式 | 表现 | 危害 |
|--------|------|------|
| 模式堆砌 | 为用模式而用模式 | 过度抽象、难读 |
| 贫血模型 | 对象只有 getter/setter，逻辑全在 Service | 逻辑散落、违背 OOP |
| 上帝类 / 大泥球 | 一个类包揽一切 | 不可维护 |
| 隐藏依赖（单例滥用） | 全局可变状态 | 测试难、并发 bug |
| 错误地抽象 | 过早抽公共基类 | YAGNI 违背，改不动 |

## 5. 现代语言改变模式用法

- **DI 容器**替代手写工厂/单例管理。
- **lambda/闭包**让策略、命令、回调变成一行，不再需要一堆类。
- **泛型**替代部分类型适配。
- 结论：模式是**思想**，不是**类模板**。用语言特性表达同一意图更简洁。

## 6. 与架构的连接

模式在类/模块层；放大到服务层就是架构模式（[[concepts/架构风格演进]]）：微服务≈多「策略+外观」的组合，事件驱动≈观察者放大。
