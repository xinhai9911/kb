# 微服务拆分实战

> 原理见 [[concepts/架构风格演进]] §2、[[concepts/领域驱动设计 DDD]]。本文给「怎么拆」的实战判断。

## 1. 拆分的边界来自业务，不是技术

```
✗ 技术层拆分（反例）：  User-Service / Order-Service / Payment-Service 都调用
                       同一个 shared-db，且 User 模块里混着认证/资料/权限
✓ 业务域拆分（正例）：  按限界上下文 —— 身份上下文 / 订单上下文 / 计费上下文
                       各自拥有数据与团队
```

- 用 **DDD 限界上下文** 找边界（[[concepts/领域驱动设计 DDD]] §2）。
- 康威定律：团队结构决定架构——一个小团队别拆太多服务。

## 2. 数据库私有化（关键决策）

| 做法 | 后果 |
|------|------|
| 所有微服务共享一个库 | 等于分布式单体，耦合回代码层 |
| **每服务私有库** | 真正解耦，但需解决跨服务数据一致 |

- 私有库后跨服务查询不能 JOIN → 用**事件同步投影 / CQRS 读模型**（[[concepts/架构风格演进]] §5）。
- 共享数据通过**事件**（领域事件，[[concepts/领域驱动设计 DDD]] §5）异步传播。

## 3. 通信选型

```
同步（请求-响应）：gRPC（内部高频）/ REST（对外）
  适用：需要立即结果的命令，如「创建订单」

异步（事件）：消息总线（Kafka/Pulsar）
  适用：结果可延迟、需广播，如「订单已支付 → 通知/积分/库存」
```
- 命令用同步，事件用异步（[[concepts/架构风格演进]] §4）。
- 避免「同步长调用链」：A→B→C→D 全同步 = 一挂全挂，用异步解耦关键路径。

## 4. 数据一致性：放弃强一致

- 跨服务不用 2PC（[[concepts/分布式系统基础]] §4），用 **Saga**：
  ```
  下单 saga: 创建订单(本地) → 扣库存(本地) → 扣款(本地)
            任一步失败 → 逆序执行补偿(释放库存/退款)
  ```
- 需**幂等**（[[concepts/分布式系统基础]] §5）+ 可补偿（每个正向操作有对应回滚）。
- 读模型接受最终一致（几秒内收敛通常可接受）。

## 5. 去中心化与团队

- 每服务自有：代码库、管线（[[concepts/CI_CD与测试策略]]）、运行、On-call。
- 公共能力（网关、可观测、鉴权）下沉为**平台/基础设施**，非每个服务各造。
- 技术栈可异构，但别过度——约定优于自由。

## 6. 拆分度权衡

| 服务太细 | 服务太粗 |
|---------|---------|
| 运维爆炸、网络跳数多、分布式事务多 | 回到单体痛点（发布耦合、故障隔离差） |

> 经验：**从粗开始**，按真实痛点（独立伸缩/独立团队/故障隔离）再拆。先用模块化单体（[[concepts/架构风格演进]] §2）。

## 7. 必须配套的能力（否则别上）

- **可观测**（[[concepts/可观测性工程]]）：没追踪定位不了跨服务慢点。
- **韧性**（[[concepts/韧性设计]]）：熔断/限流/超时防雪崩。
- **服务发现 + 配置中心**：实例动态变化。
- **网关/API**（[[concepts/API 设计]]、[[concepts/Nginx 架构与事件模型]]）。

## 8. 迁移策略：绞杀者

- 不重写，在老系统前加新服务逐步接管功能（防腐层 ACL 挡老模型）。
- 老路径流量渐切到新服务，旧代码死亡后删除。
