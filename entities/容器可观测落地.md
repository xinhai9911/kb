# 容器可观测落地（Container Observability in Practice）

> 原理见 [[concepts/可观测性工程]]（日志/指标/追踪/SLO 三支柱）；通用接入见 [[entities/可观测性接入实战]]（OTel+Prometheus+Grafana）。
> 本文只讲**容器/K8s 场景里特有的、通用笔记没覆盖的**采集机制与排障闭环。

---

## 1. 容器场景的三大信号特殊性

| 信号 | 通用做法 | 容器场景的特殊点 |
|---|---|---|
| **日志** | 落文件 | 容器** stdout/stderr 是主通道**，进程写完即走，文件在容器里随时随删 |
| **指标** | 应用暴露 `/metrics` | 还要采**容器级资源**（cAdvisor）和**集群对象级状态**（kube-state-metrics） |
| **追踪** | SDK 埋点 | 跨 **Pod/节点** 调用链，需 context 传播不因网络跳变而断 |

核心难点：**容器短命、数量大、位置漂移**——不能像虚拟机那样 SSH 上去看，必须「采集下沉到节点 + 用标签关联」。

---

## 2. 日志：从容器到后端

### 2.1 容器日志从哪来

容器运行时（containerd/runc）把容器内进程的 **stdout/stderr 重定向到宿主机文件**（默认 `json-file` 驱动，落在 `/var/log/pods/<ns>_<pod>_<id>/<container>/0.log`）。所以「看日志」本质是读宿主上的这些文件。

> [!warning] json-file 默认不轮转，会写满磁盘
> 默认每个容器日志无限增长。务必在 containerd/docker 配置里设 `max-size` / `max-file`，或在 K8s 用 `emptyDir` + 应用自己轮转。生产节点因日志爆盘是高频事故。

### 2.2 采集架构（节点级 DaemonSet）

```
容器 stdout/stderr
   │ (json-file / journald)
   ▼
节点日志文件 /var/log/pods/...
   │  Fluent Bit / Vector（DaemonSet，每节点一个）
   │  - 多行合并（stack trace）
   │  - 加标签：namespace/pod/container/node
   ▼
Loki（日志） 或  Elasticsearch（日志+检索）
   │
   ▼
Grafana 统一查询
```

```yaml
# Fluent Bit 关键配置（节选）：从容器日志文件读，加 K8s 元数据
input:
  - name: tail
    path: /var/log/containers/*.log
    multiline.parser: docker, go, java  # 合并异常栈
filter:
  - name: kubernetes
    kube_url: https://kubernetes.default.svc:443  # 补 pod/ns 标签
output:
  - name: loki
    host: loki.monitoring.svc
```

### 2.3 查询示例（Loki + Label）

```logql
# 某命名空间某容器的错误日志
{namespace="prod", container="web"} |= "ERROR"
# 统计 5xx 速率
sum by (pod) (count_over_time({container="web"} |= "5xx" [5m]))
```

## 3. 指标：容器级 + 对象级

### 3.1 cAdvisor（容器资源指标）

kubelet **内置 cAdvisor**，在 `https://<node>:10250/metrics/cadvisor` 暴露每个容器的资源用量：

| 关键指标 | 含义 |
|---|---|
| `container_cpu_usage_seconds_total` | CPU 用量 |
| `container_memory_working_set_bytes` | 工作集内存（OOM 判定依据） |
| `container_cpu_cfs_throttled_periods_total` | CPU 被限流次数（限额太小信号） |
| `container_fs_usage_bytes` | 容器文件系统用量 |
| `container_restart_count` | 重启次数 |

> 直接对应原理篇 cgroups 限额（[[concepts/容器原理与运行时#3. 基石二：Cgroups]]）：cAdvisor 读的就是 cgroup 里的计数器。

### 3.2 kube-state-metrics（集群对象状态）

cAdvisor 管「资源」，kube-state-metrics 管「对象状态」：Deployment 期望/实际副本数、Pod 相位（Pending/Running/CrashLoopBackOff）、PVC 绑定状态等。

| 关键指标 | 含义 |
|---|---|
| `kube_deployment_status_replicas_unavailable` | 不可用副本 |
| `kube_pod_status_phase{phase="Pending"}` | 长时间 Pending = 调度/资源问题 |
| `kube_pod_container_status_restarts_total` | 重启计数 |
| `kube_pod_container_status_waiting_reason{reason="CrashLoopBackOff"}` | 崩溃循环 |

### 3.3 Prometheus 抓取（kubernetes_sd 自动发现）

```yaml
scrape_configs:
- job_name: cadvisor
  kubernetes_sd_configs: [{role: node}]
  scheme: https
  tls_config: {ca_file: /var/run/secrets/...}
  bearer_token_file: /var/run/secrets/...
  relabel_configs:
  - target_label: __metrics_path__
    replacement: /metrics/cadvisor
- job_name: kube-state-metrics
  static_configs: [{targets: ['kube-state-metrics:8080']}]
```

### 3.4 容器必备告警

| 告警 | PromQL 思路 |
|---|---|
| OOM 被杀 | `increase(kube_pod_container_status_restarts_total[10m])` 且 `container_memory_working_set_bytes` 逼近 limit |
| CPU 被限流 | `rate(container_cpu_cfs_throttled_periods_total[5m])` 异常高 → 调大 `cpu limit` |
| 反复重启 | `kube_pod_container_status_restarts_total` 持续增长 |
| 调度不上 | `kube_pod_status_phase{phase="Pending"}` 持续存在 |

## 4. 追踪：跨 Pod 调用链

容器化后一次请求常跨多个 Pod/节点，必须有**分布式追踪**才能看清瓶颈。

### 4.1 关键：context 传播

用 OTel 自动埋点（多数语言 SDK 支持），通过 **W3C `traceparent` 头**在 HTTP/gRPC 调用间传递 trace_id，保证跨服务不断链。

```yaml
# OTel Collector（网关注入/汇聚）
receivers: [otlp]
processors: [batch, k8sattributes]   # k8sattributes 自动补 pod/ns 资源属性
exporters: [tempo, otlp/prometheus]  # 链路发 Tempo，指标发 Prometheus
```

### 4.2 三信号关联

- **日志 ↔ 追踪**：在日志里打印 `trace_id`，Grafana 可从 trace 跳到对应日志。
- **指标 ↔ 追踪**（Exemplar）：Prometheus 直方图样本附 `trace_id`，从慢请求指标直接下钻到具体链路。
- 一套 Grafana，三者互相跳转 = 排障闭环。

> 网络层追踪可结合 eBPF（[[concepts/eBPF 核心架构]]、[[entities/Cilium 容器网络]]）做无侵入的 Socket/Pod 级观测。

## 5. 排障闭环：RED + USE 模型

| 模型 | 维度 | 在容器里看什么 |
|---|---|---|
| **RED**（请求面） | Rate/Errors/Duration | 入口 QPS、错误率、P99 时延（应用/网关指标） |
| **USE**（资源面） | Utilization/Saturation/Errors | cAdvisor 的 CPU/内存/限流/网络（[[concepts/容器原理与运行时#3. 基石二：Cgroups]]） |

**实战示例：Pod 反复重启（CrashLoopBackOff）排查路径**

```bash
kubectl get pod <pod> -o wide          # 看状态/节点/重启次数
kubectl describe pod <pod>             # Events：镜像拉取失败？探针失败？调度失败？
kubectl logs <pod> --previous          # 看上一次崩溃的日志（关键！）
kubectl top pod <pod>                  # 看实时资源是否触 limit
# 若 OOM：调大 memory limit，或查内存泄漏（[[concepts/可观测性工程]]）
```

> [!tip] `--previous` 是救命参数
> 容器已重启，当前日志是新的空进程；`--previous` 才能看到**导致崩溃那次**的日志。

## 6. kubectl 可观测速查

```bash
kubectl top nodes / top pods           # 节点/容器资源（依赖 metrics-server）
kubectl get events --sort-by=.lastTimestamp   # 集群事件（调度/驱逐/探针）
kubectl describe pod <pod>             # 详情 + Events + 状态 + 挂载
kubectl logs <pod> -c <container> -f --tail=100
kubectl exec <pod> -c <container> -- /bin/sh   # 进容器手查（见 [[entities/容器实战]]）
kubectl get --raw /api/v1/nodes/<node>/proxy/metrics/cadvisor  # 直取 cAdvisor
```
