# 可观测性接入实战

> 原理见 [[concepts/可观测性工程]]。本文给「最小可用接入」落地（OTel + Prometheus + Grafana + Loki）。

## 1. 组件分工

```
应用 ──OTel SDK──► OTel Collector ──► Prometheus(指标) / Tempo(trace) / Loki(日志)
                                          │
                                       Grafana(统一看板+告警)
```

- **OTel Collector**：统一接收、批处理、导出到后端，应用不直接绑后端。
- **Prometheus**：拉模式采集指标，存时序。
- **Grafana**：统一查询 Prometheus/Loki/Tempo，出图与告警。

## 2. 应用埋点（OpenTelemetry）

```yaml
# otel collector 配置（最小）
receivers:
  otlp: { protocols: { grpc: {}, http: {} } }
exporters:
  prometheus: { endpoint: "0.0.0.0:8889" }
  debug: {}
service:
  pipelines:
    traces:  { receivers: [otlp], exporters: [debug] }
    metrics: { receivers: [otlp], exporters: [prometheus] }
```

```java
// Java 自动埋点：挂 agent 即可，无需改代码
-javaagent:opentelemetry-javaagent.jar
  -Dotel.service.name=order-service
  -Dotel.exporter.otlp.endpoint=http://collector:4317
```
```python
# Python 手动埋点关键路径
from opentelemetry import trace
tracer = trace.get_tracer("order")
with tracer.start_as_current_span("place_order") as span:
    span.set_attribute("order.id", oid)
    # 跨进程 context 自动随 HTTP header traceparent 传播
```

## 3. Prometheus 抓取与 PromQL

```yaml
# prometheus.yml
scrape_configs:
  - job_name: order
    static_configs: [{ targets: ["order:8889"] }]
```

```promql
# RED 指标（[[concepts/可观测性工程]] §4）
rate(http_requests_total[5m])                      # Rate
rate(http_requests_total{code=~"5.."}[5m])         # Errors
histogram_quantile(0.99, rate(http_duration_seconds_bucket[5m]))  # Duration P99
```

## 4. Grafana 最小面板

- 面板1：请求率（Rate）+ 错误率（Errors）双线。
- 面板2：P95/P99 延迟（Duration）。
- 面板3：依赖的下游延迟（trace 火焰图下钻）。
- 告警：错误率 > 1% 持续 5min → 触发（基于 SLO，[[concepts/可观测性工程]] §5）。

## 5. 日志接入 Loki

```yaml
# 应用输出结构化 JSON 日志，Promtail 采集到 Loki
# 关键：每条日志带 trace_id，与 trace 关联下钻
{"level":"info","msg":"order placed","trace_id":"abc123","order_id":"o1"}
```

## 6. 最少可行清单（MVP）

1. 装 OTel Collector + Prometheus + Grafana（docker-compose 即可）。
2. 应用挂 OTel agent，上报 service.name。
3. Prometheus 抓取，Grafana 建 RED 三面板 + P99。
4. 一条关键链路打通 trace（能看到跨服务 span）。
5. 设一个 SLO 告警（错误率/延迟）。
6. 日志带 trace_id 入 Loki，能双向跳转。

## 7. K8s / 容器场景

- 用 OpenTelemetry Operator 自动注入 sidecar/agent。
- kube-state-metrics + node_exporter 补资源层（USE 方法，[[concepts/可观测性工程]] §4）。
- 底层无侵入可观测用 eBPF（[[concepts/eBPF 核心架构]]）：网络/系统调用级。

## 8. 常见坑

| 坑 | 后果 |
|----|------|
| 只埋 metrics 不传 trace context | 链路断，定位不到慢点 |
| 日志无 trace_id | 日志与 trace 无法关联 |
| 全量采样 trace | 成本高；用尾部采样/按比例 |
| 告警基于 CPU 而非 SLO | 噪声、狼来了 |
