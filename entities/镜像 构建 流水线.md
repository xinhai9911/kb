# 镜像 构建 流水线

> 前置：[[entities/镜像格式 与 离线处理工具链]]（qemu-img / virt-customize）、[[entities/公有云镜像 制作 与 导入 实战]]（清理与导入）。
> 验收标准：[[concepts/KVM 公有云 镜像 适配]] §12；门禁工具：`projects/kvm-image-check/`。

## 1. 三条路线：按"可重复性"排序

| 路线 | 做法 | 可重复 | 适合 |
|---|---|---|---|
| **手工装机导出** | 装机 → 人工清理 → `dd`/`qemu-img` 导出 | ❌（靠人记步骤） | 一次性、探索期 |
| **自动化构建器** | Packer / diskimage-builder 声明式构建 | ✅ | **产线主流** |
| **不可变系统** | bootc / rpm-ostree 用 OCI 镜像分发系统 | ✅ | 需要原子升级与回滚的场景（见 [[concepts/容器镜像 与 系统镜像 的边界]] §4） |

> 本库现状（appliance DOM 镜像）属第一条：**建议向第二条迁移**。
> 迁移的关键不是"换成 Packer"，而是**把 §1–§4 的清理与改造步骤写成代码**。

## 2. Packer：三段式结构

```
builder（产出机器）  →  provisioner（改造机器）  →  post-processor（处理产物）
  qemu / 云插件           shell / ansible           compress / convert
```

### 2.1 qemu builder 要点

```hcl
# image.pkr.hcl（片段，示意）
source "qemu" "kvm-image" {
  iso_url      = "file:///data/iso/rhel-8-x86_64.iso"
  iso_checksum = "sha256:..."
  output_directory = "out/"
  disk_size    = "20480"                 # 20 GiB，与云上最小系统盘呼应
  format       = "qcow2"
  machine_type = "q35"                   # 现代机型；UEFI 场景配 OVMF
  firmware     = "/usr/share/OVMF/OVMF_CODE.fd"   # UEFI 构建
  ssh_username = "root"
  # kickstart/anaconda 自动安装应答（RHEL 系）
  boot_command = ["<tab> inst.ks=http://{{ .HTTPIP }}:{{ .HTTPPort }}/ks.cfg<enter>"]
}
build {
  sources = ["source.qemu.kvm-image"]
  provisioner "shell" { script = "scripts/01-dracut-virtio.sh" }
  provisioner "shell" { script = "scripts/02-install-cloudinit.sh" }
  provisioner "shell" { script = "scripts/03-sysprep-clean.sh" }   # 清理身份
  provisioner "shell" { script = "scripts/04-selfcheck.sh" }        # 自检门禁
}
```

**与云适配的对应关系**：`firmware=OVMF`（UEFI 构建）、`disk_size`（云上最小盘）、
provisioner 顺序就是 [[entities/公有云镜像 制作 与 导入 实战]] 的改造+清理清单、
最后一步就是 `check-image.sh`。

### 2.2 注意点

| 点 | 说明 |
|---|---|
| **构建机不能污染产物** | 构建期用 SSH 登录 → 会留下 authorized_keys/history（清理脚本必须覆盖） |
| **构建与验证分离** | 构建产物要另起一台"干净"VM 做启动验证，别在同一台里自证 |
| **cloud-init 的双面性** | 构建时别让它把实例身份固化进镜像；构建完清理其状态（§3 同一件事） |
| 版本化 | 输出文件名带构建号：`appliance-2026.10.16+git.abc1234.qcow2` |

## 3. diskimage-builder（OpenStack 生态）

```
elements 组合：base + vm + cloud-init + dracut-regenerate + growroot + ...
   ↓
disk-image-create -o appliance.qcow2 -t qcow2 vm cloud-init growroot rhel8
```

- **elements** 是"构建块"，可写自定义 element 把自己的改造步骤（dracut 驱动、清理、加固）封装进去
- 环境变量前缀 `DIB_*` 控制行为（如 `DIB_DISTRIBUTION_MIRROR`）
- 优点：把"镜像规格"表达为 element 集合，与 OpenStack/TripleO 流水线天然契合
- 缺点：RHEL 系支持不如 Debian/Ubuntu 顺畅，企业环境通常仍选 Packer

## 4. 后处理：virt-customize / virt-sysprep 的位置

```
构建产物（qcow2）
   → virt-customize：补驱动、装包、改配置、跑自检（不改引导结构时首选）
   → virt-sysprep：标准化清理（machine-id / ssh-hostkeys / logfiles / bash-history）
   → check-image.sh --root：门禁
   → qemu-img convert：转目标云需要的格式/压缩
   → 上传 + 导入 + 云上验收
```

> 反模式：把这些步骤做成"人工 checklist 文档"。**必须是脚本**——人一定会漏，脚本不会。

## 5. 流水线设计（推荐骨架）

```
[commit] ──► 构建（Packer/DIB）
                │
                ├─► 后处理（virt-customize + virt-sysprep）
                │
                ├─► 门禁 ①：check-image.sh --strict --root out/
                │      （FAIL 直接终止；WARN 按策略）
                │
                ├─► 门禁 ②：qemu 四挂法启动测试（自动判定"能引导 + cloud-init done"）
                │
                ├─► 产物：qcow2 + sha256 + 构建元数据（版本/git/组件清单）
                │
                ├─► 上传 OSS/OBS/COS → 导入为自定义镜像（记录镜像 ID）
                │
                └─► 云上验收：每种规格建一台实例跑 smoke（进系统/时钟 UTC/元数据可达/改密码生效）
                                      │
                                      └─► 通过 → 标记"可发布"，写入镜像目录台账
```

### 5.1 门禁 ② 的自动判定（思路）

```bash
# 起 VM 后用串口日志判定，而不是人工看屏幕
timeout 300 qemu-system-x86_64 ... -nographic -serial file:/tmp/boot.log &
# 判定：出现登录提示 且 云初始化完成
grep -q 'Reached target Multi-User' /tmp/boot.log || exit 1
```

### 5.2 版本与可追溯

| 要记录 | 为什么 |
|---|---|
| 镜像版本号 + git commit | 线上问题能回到"哪一版构建" |
| 组件清单（包版本） | 安全事件（CVE）影响面评估 |
| 云平台镜像 ID | 发布/回滚对应关系 |
| 构建时间 + 工具版本 | 复现构建 |

## 6. 回归验收集（每次出新镜像都跑）

| 层级 | 项 | 判定 |
|---|---|---|
| 离线 | `check-image.sh --strict` | 无 FAIL / 无 WARN |
| 本地 | virtio-blk、virtio-scsi、NVMe × BIOS/UEFI 四组合 | 能引导 + 有 IP + cloud-init done |
| 云上 | 目标规格矩阵（架构 × 代际 × 系统盘容量） | 能进系统 + 时钟 UTC + 元数据可达 + 改密码生效 |
| 业务 | appliance 自身 smoke（服务起来、数据面可用） | 与物理机对照 |

## 7. 常见反模式

| 反模式 | 后果 |
|---|---|
| 手工步骤只在 wiki 里 | 换人/换代即失效，镜像不可复现 |
| 构建机身份进产物 | 批量实例身份撞车（见清理清单） |
| 没门禁直接上传 | 把问题带到云上，定位成本 ×10 |
| 只在 VMware 里验证 Linux 镜像 | virtio 驱动与引导问题被掩盖 |
| 构建与发布用同一个镜像反复改 | 无法追溯"这一版到底改了什么" |
| 用"最新包"不锁版本 | 同版本号镜像内容却不同，不可复现 |
