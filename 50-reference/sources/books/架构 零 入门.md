# 软件架构书籍蒸馏（从零开始学架构）

> 李运华《从零开始学架构：照着做，你也能成为架构师》（极客时间专栏成书，330 页）。
> 一句话定位：**体系化的架构设计方法论**——以"解决软件复杂度"为唯一目的，给出三原则、四步流程，以及高性能、高可用、可扩展三大类架构模式的套路与实战案例。适合无架构经验但有编程基础、或想系统化提升的工程师。

## 一、核心思想

- **架构定义**：软件架构是"软件系统的顶层结构"。
- **架构设计目的**：为了解决**软件系统的复杂度**，不是面面俱到地给每个架构都做高性能/高可用/可扩展，而是**先识别复杂点，再针对性解决**。
- **复杂度六大来源**（第1章）：高性能、高可用、可扩展、低成本、安全、规模。绝大多数系统只需解决其中 1 个复杂度，少数 2 个；若同时 3 个以上，要么系统之前做得太烂，要么架构师判断失误。
- **架构设计思维 vs 程序设计思维**：前者关键在**判断与取舍**，后者关键在**逻辑与实现**。误区包括"架构师必须有技术天分""架构必须高大上""架构必须高可用高性能"等。

## 二、核心三原则（第2章）

原则宣言与为什么：

| 原则 | 宣言 | 核心论点 | 为什么 |
|---|---|---|---|
| **合适原则** | 合适优于业界领先 | 真正优秀的架构是在企业当前人力、条件、业务等约束下设计出来的，能整合资源发挥最大功效并快速落地 | ①将军难打无兵之仗（没人）；②罗马不是一天建成的（没积累）；③冰山下面才是关键（没有对应业务场景，幻想灵光一闪成天才）。BAT 出来的架构师到小公司生搬硬套常失败 |
| **简单原则** | 简单优于复杂 | 软件领域的"复杂"代表"问题"，而非"先进"。复杂性分两类：结构复杂性（组件多→故障率高、改动波及广、定位难）与逻辑复杂性（单组件承担过多功能/复杂算法） | 电路设计好后不变，复杂性只在设计时有影响；软件投入运行后持续修改，复杂性全生命周期都有害。KISS 原则适用 |
| **演化原则** | 演化优于一步到位 | 软件架构需随业务发展不断演化，类似生物演化（适应环境→迭代繁殖→环境变则改变） | 建筑永恒是主题，软件变化才是主题。Windows 8 与 1.0、Android 6.0 与 1.6 已是两个不同系统。不可能 1985 年设计出 Windows 8 |

> 提炼：不要贪大求全、不要盲目照搬大公司方案，认真分析当前业务特点，设计合理架构快速落地，再持续完善。

## 三、架构设计四步流程（第3章）

### 3.1 识别复杂度（有的放矢）
- 本质目的决定先分析系统复杂性；判断错复杂度，后续方案再先进也是南辕北辙（如业务逻辑复杂却设计了 TPS 5万 的高性能架构）。
- 复杂度一般只源于某 1 个方面，少数 2 个。若同时多个，应**逐个解决、按优先级排序**，不要幻想一次重构解决所有问题。

### 3.2 设计备选方案（按图索骥）
- 成熟架构师=熟悉已有技术+烂熟经过验证的架构模式+按业务挑选组合+调整，而非凭空创新。
- 常见错误：①设计"最优秀"方案（违反简单原则）；②只做 1 个方案（过度辩护、思维局限）；③备选方案过于详细（陷于细节、评审效果差）。
- 正确做法：**3～5 个备选**；方案间**差异要明显**（如主备 vs 集群、ZooKeeper vs Keepalived 决策）；技术**不局限于熟悉的技术**（避免"手里只有锤子看什么都是钉子"）。

### 3.3 评估和选择备选方案（深思熟虑）
- 难点：每个方案都可行、都不完美、评价标准主观。
- 错误做法：①最简派/最牛派/最熟派/领导派（场景化选择）；②数量对比法（等同看待质量属性重要性）；③加权法（权重无法客观给出，易成数字游戏）。
- **正确做法：360 度环评 + 按优先级选择**。列出关注的质量属性（性能、可用性、硬件成本、项目投入、复杂度、安全性、可扩展性），逐属性对比各方案；再按业务/团队/发展阶段排定属性**优先级**，优先满足第一优先级，依次类推。
- 业务规模评估经验：当前基数低×4、基数高×2（如 TPS 1000→按 4000 设计）。遵循演化原则，避免过度设计。

### 3.4 详细方案设计（精雕细琢）
- 将选定备选方案细化：确定关键技术细节（如 ES 索引划分/副本数、MySQL 分库分表维度/联合查询处理、Nginx 负载均衡策略）。
- 注意：详细设计若发现备选不可行，通常因遗漏关键技术点/质量属性（如忽略开发周期导致要开发 1 年而废弃）。
- 避免成为"PPT 架构师"：架构师须对备选方案关键细节有深入理解；通过分步/分阶段/分系统降低复杂度；复杂方案用设计团队博采众长。

## 四、高性能架构（第2部分）

### 4.1 存储高性能（第4章）
**读写分离**
- 本质：将访问压力分散到多节点，但**不分散存储压力**。主从集群（主机读写、从机只读），主机复制数据到从机。
- 核心问题：**复制延迟**（MySQL 可达 1s，大量同步可达 1 分钟）。应对：①写后读指定发主机（业务强绑定）；②读从机失败二次读主机（"二次读取"，对主机压力大）；③关键业务读写全走主机，非关键业务读写分离。

**分库分表**
- 业务分库（按模块分散）：带来 join 失效、分布式事务（XA 性能低）、成本 3 倍等问题。初创业务不建议一开始就分库（不确定性高、拖慢节奏）；单台 DB 一般能支撑 10 万用户量级。
- 分表：垂直分表（不常用大字段拆出）+ 水平分表（按行切分）。垂直适合"占空间但不常查"的列；水平适合单表数据达瓶颈。
- 提炼：分库分表分散存储与访问压力，但引入 join/事务/映射复杂性——"合适原则"取舍。

**NoSQL 场景**（第4.2节）
- K-V（Memcache/Redis）：简单 KV、缓存；文档（MongoDB）：嵌套结构数据；列式（HBase）：海量数据按列分析；全文搜索引擎（Elasticsearch）：倒排索引做搜索。
- 提炼：NoSQL 是 SQL 的补充（Not Only SQL），弥补关系库在性能/数据结构上的不足。

### 4.2 计算高性能（第5章）
**单服务器模式演进**
- PPC（Process per Connection）、prefork、TPC（Thread per Connection）、pre-thread：每连接建进程/线程，连接结束销毁，资源浪费大。
- **Reactor 模式**（反应堆/Dispatcher）：I/O 多路复用 + 线程池。核心= Reactor（监听并分配事件）+ 处理资源池。三种实现：单 Reactor 单进程（Redis 用）、单 Reactor 多线程、多 Reactor 多进程/线程（Netty/Nginx/Memcache 据此）。
- **Proactor 模式**：异步 I/O，由操作系统完成 I/O 后通知，与 Reactor 的"同步 I/O 多路复用"相对。
- 提炼：Reactor 解决"一个进程高效处理多连接"，是高并发服务器的基石模式。

**集群高性能 + 负载均衡**
- 分类：DNS 负载均衡（地理级，简单成本低，但粒度粗、算法少、缓存久）、硬件（F5）、软件（LVS 4层 / HAProxy / Nginx 7层）。
- 算法：轮询、加权轮询、最小连接、源 IP hash、一致性 hash 等。

### 4.3 缓存（第4.3节）
| 问题 | 含义 | 应对 |
|---|---|---|
| **缓存穿透** | 缓存没发挥作用（数据不存在 / 生成缓存耗时长），每次都回源 | 查不到则缓存默认值（空值）；爬虫遍历类无太好办法，靠识别+监控 |
| **缓存雪崩** | 缓存集中失效，瞬间大量请求回源拖垮存储 | ①更新锁（分布式需用 ZooKeeper 锁）；②后台更新（缓存永久+后台线程定时刷新，支持缓存预热） |
| **缓存热点** | 单份热点数据压垮单台缓存 | 复制多份缓存（key 加编号），请求随机分散 |

## 五、高可用架构（第3部分）

### 5.1 CAP 与 BASE（第6章）
- CAP：一致性、可用性、分区容错；分布式系统必须容忍分区（P），故实际是 **CP** 或 **AP** 取舍。
- ACID（事务）vs BASE：基本可用、软状态、最终一致——接受短暂不一致换可用性。

### 5.2 高可用设计 + FMEA（第7章）
- **FMEA（故障模式与影响分析）**：源于美国军方/阿波罗计划，是一套"分析与思考方法"而非工具。架构设计后用它找可用性隐患。
- 方法：①给出初始架构图 → ②假设某部件故障 → ③分析对功能的影响 → ④判断是否需要优化。
- FMEA 分析表字段：功能点（**从用户角度**，如"登录""注册"，非模块角度）、故障模式（精确量化，如"MySQL 响应达 3s"而非"慢"）、故障影响、严重程度（致命/高/中/低/无，=功能重要度×影响范围×受损程度）、故障原因、故障概率（高/中/低）、风险程度（=严重度×概率）、已有措施、规避措施、解决措施、后续规划。
- 实战：用户管理系统（MySQL+Memcache）经 FMEA 得出改进——MySQL 增备机、MC 扩集群、MySQL 双网卡。

### 5.3 存储高可用（第8章）
- 本质：数据复制到多设备实现冗余，复杂性在**复制延迟/中断导致的不一致**。
- 模式：主备复制、主从复制（从机提供读）、多副本。
- **一致性算法**（复制状态机：各节点含完整状态机副本，算法协调保持一致）：
  - **Paxos**：理论证明正确，但极难理解、缺细节难实现（Google Chubby 也只能 Paxos-like）。多数一致性（Quorum），2n+1 节点中 n+1 一致即可。角色是逻辑划分。
  - **Raft**：为工程实践设计，首要目标"可理解性"。拆为 Leader 选举/日志复制/安全保证三子问题，论文含实现细节（约 2000 行 C++）。
  - **ZAB**（ZooKeeper）：类似 Raft 强化 Leader，但用 primary-backup 复制（Leader 执行后复制结果），而 Paxos/Raft 用 state machine replication（各节点复制操作各自执行）。
- **数据分区**（地理级容灾）：按规则分区分布不同地理位置，规避城市级灾难（新奥尔良水灾、美加大停电等）。

### 5.4 业务高可用（第10章）
**异地多活**
- 分类：同城异区（近同机房）、跨城异地（距离远、网络延迟复杂）、跨国异地（只读/不同地区服务）。
- 设计四步：①**业务分级**（挑核心业务做多活）；②**数据特性分析**（唯一性、实时性、可丢失性、可恢复性）；③**数据同步**（存储系统同步如 MySQL 主从、消息队列同步、重复生成如 session/cookie）；④**异常处理**（多通道同步、同步与访问结合、日志记录、用户安抚）。
- 设计技巧：保证核心业务多活、保证核心数据最终一致、多种手段同步、只保证绝大部分用户多活。

**接口级故障应对（降级/熔断/限流/排队）**
| 手段 | 角度 | 核心思想 | 实现要点 |
|---|---|---|---|
| **降级** | 系统功能优先级 | 丢车保帅，优先保核心 | 系统后门降级（URL）、独立降级系统 |
| **熔断** | 依赖的外部系统故障 | 避免被慢依赖拖死 | 统一 API 调用层采样统计；阈值设计（如 1 分钟内 30% 请求 >1s 即熔断） |
| **限流** | 用户访问压力 | 只放能承受的量进来 | 基于请求（限总量/限时间量）、基于资源（连接数/队列/CPU）；阈值靠压测+逐步优化 |
| **排队** | 限流变种 | 让用户等而非直接拒 | 独立排队系统（如 Kafka），调度模块动态拉取 |

## 六、可扩展架构（第4部分）

### 6.1 可扩展基本思想（第11章）
- 万变不离其宗：**拆！** 减少改动范围、降低风险。
- 三种拆分思路：**面向流程**（展示层→业务层→数据层→存储层，对应分层架构）、**面向服务**（对应 SOA/微服务）、**面向功能**（对应微内核架构）。可组合使用（如整体微服务 + 某服务内部分层 + 某服务微内核）。

### 6.2 AKF 扩展立方体（可扩展模式）
- **X 轴**：水平复制（多实例无差别克隆），解决容量与可用性。
- **Y 轴**：按业务/服务/功能拆分（面向服务/功能），解决耦合与复杂度。
- **Z 轴**：按数据/客户/地域分区（如按用户 ID 取模、按地区），解决数据规模与就近访问。
- 提炼：X 解决"量"、Y 解决"耦"、Z 解决"数据分布"，三者叠加即无限扩展。

### 6.3 微服务（第14章）
- **与 SOA 关系**：SOA 因企业 IT 庞大复杂、改造成本高但需互通而生；微服务是另一理念，并非孰优孰劣，场景不同。微服务生搬硬套进企业 IT 可能改造成本远超 SOA。
- **陷阱**：①服务划分过细→系统间复杂度上升；②服务数量多→团队效率降（5~6 人拆 30+ 服务）；③调用链长→性能下降（6 次调用≈300ms）、问题定位难；④无自动化支撑→无法快速交付；⑤无服务治理→数量多了管理混乱（路由/故障隔离/注册发现）。
- **最佳实践**：
  - 服务粒度——**"三个火枪手"**：1 个服务 3 人负责（系统复杂度刚好、稳定备份、有效讨论）。源于贝索斯"两个披萨"团队理论。
  - 拆分方法——基于业务逻辑、可扩展性、可靠性、性能等维度自由组合。
  - 基础设施（成败关键在 **automated**）：自动化测试、自动化部署、配置中心、接口框架（统一 HTTP/JSON 规范）、API 网关（接入鉴权/权限/路由/流控）、服务发现（自理式 vs 代理式）、服务路由、服务容错（重试/流控/隔离）、服务监控、服务跟踪（基于 Google Dapper，span/parentId 串联，采样跟踪+染色跟踪）、服务安全（接入安全/数据安全/传输安全）。
  - 提炼：微服务并未减少复杂度，只是把 ESB 的复杂度转移到基础设施。

### 6.4 消息队列（第16章，实战）
- 案例"前浪微博"：系统间用接口调用耦合（一条微博十几处通知）。架构设计"知行合一"——灵活用原则/模式。关键点：消息队列用于**异步解耦**、削峰填谷；设计需考虑协议、存储、消费模型、高可用。

### 6.5 存储选型与负载均衡分层（第14~15、18章）
- **存储选型**：SQL（MySQL/PostgreSQL 开源，分库分表后常独立为中间件如 TDDL/DBProxy；大厂建 SQL 存储平台如淘宝 UMP）、NoSQL（K-V/文档/列式，本身带集群，规模大后建统一存储平台）、小文件（商品图/微博，建统一平台如 TFS/JFS/Haystack）、大文件（视频/日志，Hadoop 生态 HDFS/HBase/Storm/Hive）。
- **负载均衡分层**：DNS（地理级）→ 硬件 F5 / 软件 LVS（4层）→ Nginx/HAProxy（7层）→ 应用内。每层职责与性能/成本/算法能力不同。

## 七、互联网架构模板（第18章）

标准技术架构（BAT 及全行业殊途同归）：

```
用户层 → 业务层 → 服务层 → 数据层（存储层：SQL/NoSQL/小文件/大文件）
              ↑
        开发层（框架/中间件）
              ↑
   运维平台 / 测试平台 / 数据平台 / 管理平台
              ↑
         网关层（接入/路由/限流）
```

- 存储层：SQL、NoSQL、小文件存储、大文件存储，规模大后均演进为统一存储平台。
- 开发层：开发框架、Web 服务器、容器、微服务、消息队列、RPC、ORM 等。
- 平台层：运维（监控/部署）、测试（自动化/性能）、数据（大数据平台）、管理（配置/权限）。
- 提炼：创业公司理解此模板即可对照补齐技术栈，不必崇拜 BAT。

## 八、架构重构（第19章）

- 目的仍是"解决复杂度"。案例：M 系统（后台，性能非关键，关键是数据耦合→目标数据解耦）；S 系统（亿级访问，全局单点→目标高可用）；X 系统（大而全+整站挂→目标拆分子系统，先解耦才能解可用）。
- **重构策略——分段实施**：
  1. **划分优先级**：明显紧急的先落地（如扩容防超时/过载）。
  2. **问题分类**：每阶段集中解决一类（如统一公共组件）。
  3. **先易后难**：易的问题先解决后，难题可能变易甚至消失；快速见效提士气；过程中暴露遗漏/误判及时调整。
- **架构师"文武双全"**：项目管理能力（文：找目标/协调/规划）+ 技术能力（武：微观并发框架、宏观选型、业务可扩展性设计）。识别重构目标 = 回到"架构设计为解决复杂度"。

## 九、各部分"可提炼要点（实证）"小结

- **原则层**：合适/简单/演化三原则是全书价值观底座，所有模式取舍都回到它。
- **流程层**：识别复杂度→3~5 备选→360 度环评按优先级选→详细设计；反对"最优秀/只一个/过度详细"三误区。
- **高性能**：读写分离（复制延迟）、分库分表（join/事务代价）、NoSQL 补位、Reactor 单服务器高并发、负载均衡分层。
- **高可用**：CAP 取舍、FMEA 表、存储复制+一致性算法（Paxos/Raft/ZAB）、异地多活四步、降级/熔断/限流/排队。
- **可扩展**：拆字诀（流程/服务/功能）、AKF 三轴、微服务陷阱与基础设施、消息队列解耦。
- **模板与重构**：行业统一技术架构；重构分段实施、先易后难、文武双全。
