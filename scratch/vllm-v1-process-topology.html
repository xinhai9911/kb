② 三者关系速查表（谁认识谁）

关系创建（spawn）通信（ZMQ）一句话
主进程 → EngineCore ✅ 主进程拉起它 ✅ 每步都在传请求/收输出 前厅把单子递给大脑
EngineCore → Worker ✅ 它内部的 Executor 拉起 ✅ 广播调度结果、收执行结果 大脑把活分给车间
主进程 ↔ Worker ✕ 不创建 ✕ 不通信 互相根本不知道对方存在——一切经 EngineCore 转发
Worker ↔ Worker — ✅ 集合通信（gloo/NCCL，TP 时用） 张量并行时切片交换（CPU 单机一般用不到）
💡 一句话记住：主进程生EngineCore，EngineCore生Worker； 前两者像前台和厨房经理（谈订单），后两者像厨房经理和厨师（派工）； 主进程和Worker之间没有电话线——订单与菜都由经理中转。

④ 为什么要拆进程 & 为什么之后不能改

🧵 GIL：一个进程只有一把「话筒」

Python 同一进程内同一时刻只有一个线程执行字节码。若调度循环和 API 收发同居一进程（v0），三方抢同一把 GIL，调度被卡顿。拆成三个进程后各拿各的话筒，调度可常驻满载。

附赠：进程隔离 —— 调度崩溃不拖 Worker；EngineCoreSentinel 可做容错监控。

🧊 冻结点：为什么之后无法改并行规模

这一步完成后以下东西已按 world_size/rank 物化：

  • ZMQ socket 已绑定、进程间管道已建立
  • gloo/NCCL 通信组已初始化（rank 已分配）
  • Worker 进程已按规模拉起（OS 级资源）
  • 后续 KV 池、编译缓存（CUDA Graph 档位）都按此拓扑分配

改 tensor_parallel_size / DP 数 = 换拓扑 = 只能重启。CPU 绑核也在这前后发生。

⑤ 日志排障核对清单

  • Config: 大段 → 核对真正生效的 enforce_eager / tensor_parallel_size / max_model_len；与命令行对不上 = 参数没传进去
  • world_size / rank → 并行规模是否符合预期（CPU 应为 1）
  • READY 回执 → max_model_len / num_gpu_blocks 是 auto-fit 后的值，可能与配置不同
  • 想同进程调试 → VLLM_ENABLE_V1_MULTIPROCESSING=0 回退 v0 风格同进程
  • 报错定位 → 主进程报错在 API 层；EngineCore 报错在调度/内存；Worker 报错在模型执行/内核
