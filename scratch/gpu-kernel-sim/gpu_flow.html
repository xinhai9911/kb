1

编码 CPU

写 CUDA C 源码

人类写下 vector_add.cu：C[i] = A[i] + B[i]，每个 GPU 线程负责一个元素。此刻它只是文本文件，GPU 完全不认识它。

__global__ void vector_add(const float* A, const float* B, float* C, int N) { int i = blockIdx.x * blockDim.x + threadIdx.x; // 我是几号线程？ if (i < N) { C[i] = A[i] + B[i]; } // 越界的线程摸鱼 }
2

编译 → PTX CPU

nvcc · 虚拟 ISA

nvcc 把 C 代码翻译成 PTX——文本汇编、不绑定具体芯片。它是留给驱动 JIT 的"备胎"：新显卡没有现成机器码时，驱动现场把它编成 SASS（这就是老 PyTorch 在新卡上首跑巨慢的原因）。

ld.global.f32 %f1, [%rd5]; // 从显存读 A[i] add.f32 %f3, %f1, %f2; // 算加法 st.global.f32 [%rd7], %f3; // 写回 C[i]
3

汇编 → SASS CPU

ptxas · 真实机器码

ptxas 把 PTX 压成 SASS：无限虚拟寄存器 %r2~%r7 压进有限的物理寄存器（本例每线程 4 个），指令编码成二进制字。SASS 只认一种架构（sm_80/sm_89/…），换卡就要换 SASS。

/*0040*/ LDG.E R4, [R2] // 读 A[i] /*0050*/ LDG.E R5, [R3] // 读 B[i]（调度在两条读之间插了别的活） /*0060*/ FADD R4, R4, R5 // 加 /*0070*/ STG.E [R6], R4 // 写 C[i] /*0080*/ EXIT
4

打包 cubin CPU

ELF 格式二进制

SASS + 元数据（每线程寄存器数、共享内存用量）打包成 cubin——本质是 ELF 文件，和 Linux 可执行文件同宗。文件开头固定是 7f 45 4c 46（\x7fELF），驱动加载第一步就验这四个字节。

7f 45 4c 46 | ELF头 | .text(SASS指令) | .info(4寄存器,128线程) | 段头表 | ↑ magic ↑ 64B ↑ 40字节代码 ↑ 元数据 ↑ 目录

模拟器实测：399 字节，md5 指纹 4267fb20b4be（真实工具链拿 cubin 做编译缓存键）。

↓ 接下来进入运行期：前 4 步只发生一次，后面每次进程启动都要走 5~8
5

驱动加载 CPU

cuModuleLoad

进程首次用到这个 kernel 时，驱动读 cubin：验 magic → 按段头表找到 .text → 把 SASS 上传到显存（模拟器放在 0x1000）→ 按当前 GPU 架构挑机器码（没有就 JIT PTX）→ 登记函数句柄，同时读出元数据（用多少寄存器/共享内存——决定了每个 SM 能塞几个 block）。

磁盘 cubin ──解析──► 显存 0x1000: [LDG.E][LDG.E][FADD][STG.E][EXIT] └─ 从此 kernel 的"肉身"就住在显存里
6

H2D 搬数据 跨界

cudaMemcpy Host→Device

输入向量住在CPU 内存条里，GPU 够不着。DMA 拷贝引擎（不是 SM！）把字节穿过 PCIe 写进显存：A@0x20000、B@0x30000。这纯粹是搬运，不算数。

CPU 内存条 PCIe (~25GB/s) 显存 [1,2,3,4,5,6,7,8] ═════════════════════► 0x20000 (A) [10,20,...,80] ═════════════════════► 0x30000 (B) 数据就位，等着

vLLM 启动慢的主因：几十 GB 权重就是这样一次性搬进显存的。

7

Launch 发令 跨界命令

kernel<<<grid, block>>>(…)

最易误解：launch 传的不是数据，是地址。参数打包成 param buffer（模拟器输出里可见 A=0x20000, B=0x30000, C=0x40000, N=8 的字节排布），组装成命令写进 pushbuffer，再碰门铃通知 GPU。CPU 侧 5~10µs 固定开销全部花在这条路径上。

param buffer（28字节，无一字节是数据本身）: 0000020000000000 A 的地址 0000030000000000 B 的地址 0000040000000000 C 的地址 08000000 N=8 │ 写入 pushbuffer → 碰门铃 ▼ GPU 命令处理器: 取命令 → GigaThread 把 1 个 block 派给某 SM → block 拆成 warp(32线程) → warp 锁步执行 SASS → 执行到 LDG.E 时才第一次真正去读 0x20000 —— 读到的正是第6步放好的数
8

D2H 收结果 跨界

cudaMemcpy Device→Host

GPU 把 C[i]=A[i]+B[i] 写进显存 0x40000，但 CPU 看不见自己的答案——再由 DMA 引擎把结果穿过 PCIe 搬回内存条，与 CPU 计算对照校验：[11,22,…,88] ✅ 通过。

显存 0x40000: [11,22,33,44,55,66,77,88] ══════════════ PCIe ══════════════► CPU 内存条 → 校验 ✅
顺序坑：若先 launch 后 H2D，kernel 读到的是显存残留 → 一声不吭算出垃圾，不报错不崩溃。这就是"数据必须先于命令就位"的原因。

🧩 一图收束：三种命令、两个执行者

步骤 6(H2D)、7(launch)、8(D2H) 本质上都是写进同一个 pushbuffer 的命令， 只是执行者不同：搬数据的命令由 DMA 拷贝引擎执行， launch 由 GigaThread→SM 执行。CUDA Graph 做的事 = 把这串命令流原样录制，重放时 GPU 命令处理器自己消化——CPU 全程旁路， 这正是 enforce_eager=True 关掉的优化。

pushbuffer 命令流： [H2D 拷贝A] [H2D 拷贝B] [launch vector_add] [D2H 拷贝C] ▲ DMA引擎执行 ▲ SM执行 ▲ DMA引擎执行
