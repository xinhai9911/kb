# 推理引擎 性能对照与基准

> ⚠️ **先读声明**：本文不是"实测报告"。
> - 数字来自 vLLM 论文/官方博客、SGLang 官方博客、TensorRT-LLM 官方说明、llama.cpp 的 `llama-bench` 社区结果等在 **各自口径、各自硬件** 下给出的**公开量级**；
> - **不同引擎的口径不可直接横比**（输入输出长度分布、并发、并行度、量化、GPU 型号都影响巨大）；
> - 本环境无法访问外网核对最新基准。**想要能用的数字，用 §4 的方法在自家硬件上跑**，然后回填本表。
> - 结论性原则（比具体数字更可靠）：**性能不是引擎属性，是「负载 × 硬件 × 配置」的电光匹配结果**。

## 1. 公开量级参考表（非实测，仅供量级感知）

| 引擎 | 典型硬件 | 典型量级参考 | 备注（来源口径） |
|------|----------|---------------|------------------|
| **vLLM** | A100-80G / H100 | Llama-3.1-8B 单卡稳态吞吐 **数千 tok/s** 量级；TTFT 数十~数百 ms（随并发/isl） | vLLM "Anatomy" 博客/官方 benchmark；吞吐量对 batch 数高度敏感 |
| **SGLang** | 同左（常对标 vLLM） | 通用负载 ≈ vLLM 同档；**高前缀复用/长上下文/多轮负载自称优于 vLLM（blog 口径提到提升约 1.1×~2.7×，视负载）** | SGLang 官方博客 benchmark；提升集中在前缀缓存命中高的场景 |
| **TensorRT-LLM** | NVIDIA 专属 | 官方口径常"比基线快 X%"；对 NVIDIA 栈（FP8、图融合）挖得最深 | NVIDIA 官方基准，口径与 vLLM/SGLang 不同 |
| **llama.cpp** | CPU / Apple / 低端 GPU | 7B Q4：桌面 CPU **10~30 tok/s** 量级、Apple M 系 **40~+70 tok/s**、NVIDIA 4070 级 **70~150 tok/s**（社区 llama-bench 结果） | 本地单用户体验级；绝对吞吐不敌数据中心引擎 |

> 说明：vLLM/SGLang 的"数千 tok/s"是**服务端大并发稳态吞吐**（同一批里 N 个请求共享前向），不是单客户端速度；llama.cpp 的 tok/s 常是单用户逐 token 延迟换算。两者不在一个量纲——横向比没意义，这正是 §4 必须自测的原因。

## 2. 该看哪些指标（别只盯吞吐）

| 指标 | 含义 | 谁在意 |
|------|------|--------|
| **TTFT**（Time-To-First-Token）| 请求发出→首个 token 输出的延迟 | 交互/客服，影响"响应感" |
| **ITL / TPOT**（Inter-Token / Time-Per-Output-Token）| 相邻输出 token 间隔 | 流式打字体验 |
| **吞吐 tok/s** | 稳态每秒输出 token 总数 | 计费/成本、并发容量 |
| **KV 使用率 / 并发上限** | 同显存能撑多少并发 | 容量规划 |
| **每百万 token 成本** ($/1M tok) | 折算电费+折旧 | 算账 |
| **P99 / P99.9** | 尾部延迟（用户感知的"卡顿"） | SLA |

> 经验：**压测看 P99，投产看成本**；单点均值（avg)会被 outlier 掩盖。

## 3. 负载→引擎的初步判据（选型速查）

| 负载画像 | 倾向引擎 | 理由 |
|----------|----------|------|
| 超高并发通用 API 服务 | vLLM | 最成熟、生态最大、参数/运维文档全 |
| 长 system prompt / 多轮 / Agent / 树搜索（高前缀复用） | SGLang | RadixAttention 前缀缓存收益最大；DeepSeek 官方推荐 |
| NVIDIA 全栈、要榨干单卡（FP8/图融合） | TensorRT-LLM | 官方闭环优化 |
| CPU/苹果芯片/离线/个人工具 | llama.cpp | 跨平台、量化移植性最强 |
| 团队已有 HuggingFace 生态/rebuild 频繁 | vLLM（+HF 集成） | 模型支持最广、切模型最快 |
| 需要 JSON/约束输出为主 | SGLang（原生）/ vLLM（guided） | 前者 DSL+约束第一公民 |

> 深入选型见 [[sources/推理引擎/推理 引擎 选择]]；原则/调优/监控对应 [[sources/推理引擎/推理 引擎 原则]]、[[sources/推理引擎/推理 引擎 调优]]、[[sources/推理引擎/推理 引擎 监控]]。

## 4. 自测基准方法论（把这张表填上你自己的数字）

### 4.1 用引擎自带的基准工具（最省事、口径最一致）

```bash
# vLLM 自带的跨后端压测（vllm/vllm-openai 镜像自带）
vllm bench serve \
  --backend vllm --model meta-llama/Llama-3.1-8B-Instruct \
  --dataset-name sharegpt --dataset-path ./sharegpt.json \
  --num-prompts 256 --max-connections 64

# SGLang 自带基准（sglang/benchmark/bench_serving.py）
python -m sglang.bench_serving --backend sglang \
  --model meta-llama/Llama-3.1-8B-Instruct \
  --dataset-name sharegpt --dataset-path ./sharegpt.json \
  --num-prompt 256

# llama.cpp 自带微基准（逐 token 数据更直观）
llama-bench -m Llama-3-8B-Q4_K_M.gguf -p 512 -n 128 -t 8 -ngl 24
```

### 4.2 保证可比的硬性条件（缺一个就白测）

1. **同一份模型文件/同一量化**（Q4 vs FP8 不可比）；
2. **同一输入输出分布**：`sharegpt`（普通对话）、`long-sharegpt`（长上下文）等数据集原样用于两端；
3. **同一并发/批参数**：`--num-prompts`、`--max-num-seqs`、`--max-num-batched-tokens` 对齐到引擎等效值；
4. **同一硬件与显存分配**：同卡、同 `gpu_memory_utilization`（GPU 的 0.9 与 0.85 都不算同一档）；
5. **预热**：前 N 个请求弃用（英文叫 warmup），避免 CUDA Graph 首次捕获的虚高/虚低；
6. **稳态 vs 冷启**：TTFT 分 warm/cold 两档看 P50 与 P99。

### 4.3 外部压测工具（做端到端 SLA）

- **静态**：`wrk`/`ghz`/`hey` 打 HTTP 压力，或 **FastChat serve**、**Locust** 模拟真实会话；
- **流式**：确认 SSE 逐帧间隔（抓包或 SDK 计时）；
- **监控对账**：把 `/metrics`（vLLM）/Prometheus 指标与压测结果对起来，看瓶颈是调度还是 kernel。

### 4.4 回填建议格式

每次自测记录：`引擎/版本 / 模型 / 量化 / 卡 / TP/PP/EP/DP / 并发 / isl分布(osl) / TTFT-P50/P99 / ITL / 吞吐 / 显存峰`。**同样的七个字段**跨引擎记录才有意义。

## 5. 成本粗算

```
min-per-1M-tok ≈ 运行该模型的每秒成本 × 1e6 ÷ 每百万 token 所需秒数
  ≈ (卡月成本 ÷ 月秒数) × (1e6 ÷ 稳态吞吐 tok/s)
```
- 容量规划：`并发上限 ≈ KV cache 容量 ÷ 每请求平均 KV 占用`；KV 分页/前缀缓存/FP8 KV 直接改变这分母。
